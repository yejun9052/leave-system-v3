원본: [휴가관리 시스템 V2 — 설계 문서](https://app.notion.com/p/3de2735d989181df93e7f7670927c0c9). 원본은 설계 이력으로 보존한다. 이 문서와 원본이 충돌하면 **확정된 결정과 아래 수정 설계**를 우선한다. 변경되지 않은 화면·API·기능 설명은 원본을 참조한다. 이 문서는 구현 완료나 운영 검증을 뜻하지 않는다.

## 1. 구현 전·운영 전 필수 정리

### 구현 전 필수

1. **원장 동시성·겹침** — 서로 다른 신청이 같은 사원의 같은 날짜·반차 시간대를 차지하지 못하게 DB 제약을 둔다. 신청, 최종 승인, 취소, 정정, 대리 등록, 날짜 작업, 이관이 동일한 잠금 순서와 트랜잭션 규칙을 사용한다. 신청 ID별 `USE` 멱등성 키만으로는 다른 신청끼리의 날짜 겹침을 막을 수 없다.
2. **날짜별 휴가 상태와 환급** — 다일 신청 중 임시공휴일이 된 하루만 제외하고 그 하루의 연차만 돌려준다. 신청 전체 취소·재신청 방식은 사용하지 않는다. 승인·잔여·달력·부재 계산은 실제 유효 날짜를 기준으로 한다.
3. **기존 Excel 이관 순서** — 과거 사용 이력을 넣기 전에 과거 부여·소멸을 확정하면 잔여가 틀릴 수 있다. 실무에서 이관 범위와 기준 잔액을 확인한 후 미리보기·대조·승인 과정을 거쳐 반영한다. 같은 파일이나 같은 원천 행의 중복 반영을 막는다.
4. **계정·권한** — 시스템 관리자 계정은 처음에 1개만 발급해 담당자를 정한다. 코드에 고정된 기본 비밀번호를 두지 않는다. 휴직자는 로그인·조회만 허용하고, 퇴직자는 로그인할 수 없게 한다. 상태·역할 변경은 기존 세션에도 반영한다. 관리자 계정을 여러 사람이 사용하면 감사 기록으로 실제 행위자를 구별할 수 없으므로 운영 방식을 별도로 정해야 한다.
5. **법정 장기휴가** — 경조사의 `본인 출산 90일` 고정 항목으로 처리하지 않는다. 법정휴가·휴직을 별도 종류와 기간 기록으로 관리하고, 상세 기간 규칙은 실무·노무 확인 후 정한다.
6. **결재·인원 재검사** — 인원 부족이어도 신청은 접수하고 경고한다. 팀 기준과 전사 기준의 판단 권한을 나누고, 팀장 확인 뒤 최종 승인 직전에 다시 계산한다. 취소 요청 중인 승인 휴가도 계속 부재로 센다.

### 운영 전 필수

1. **백업·복구** — 운영 DB가 원장이 되므로 자동 백업, 운영 서버 밖의 보관 장소, 실패 알림, 분리된 복원 검증 환경과 복구 절차가 첫 운영의 필수 조건이다. 운영 DB를 덮어쓰는 웹 복원 기능은 두지 않는다.
2. **감사 기록 보존** — 애플리케이션에서 로그·원장 행을 고치거나 지우는 경로를 제공하지 않는다. 운영 DB 계정의 권한을 제한하고 외부 사본을 남긴다. 서버·DB 관리자까지 포함해 삭제를 막거나 탐지할 수 있는 독립 저장소와 관리 주체는 인프라 확인이 필요하다.
3. **원장 전환** — 실무가 승인한 Excel 이관 결과와 시스템 잔액이 맞고 백업·복원 절차가 준비된 뒤에만 기존 Excel을 대체한다. 개발 환경에서의 실험이 운영 복구 검증을 대신하지 않는다.
4. **개인정보·법정 규칙** — 달력에 보이는 병가 등 휴가 종류, 감사 기록 보존기간, 연차 부여·소멸·사용 촉진·법정휴가 규칙은 담당자 확인 뒤 운영 설정에 반영한다.

## 2. 목적, 범위, 결정 상태

- 약 50명이 사용하는 내부 휴가 시스템이다. 신청·승인·취소·잔여 연차·휴가 현황을 한 곳에서 관리하고, 운영 전환 후 시스템의 연차 원장을 기준 기록으로 삼는다.
- 첫 운영 범위에 로그인·역할, 사원·부서, 휴가 신청과 결재, 날짜별 원장, Excel 이관·현황 내보내기, 회사 달력, 공지·알림, 법정 장기휴가 등록, 백업·복원 절차, 감사 기록을 포함한다.
- Google OAuth와 회사 SMTP는 사용 가능하다고 **가정**한다. 배포 전 연동 가능성을 확인한다. 불가능하면 로그인·초기 비밀번호 전달·알림에 대체 절차를 명시한 후 전환한다.
- 휴가 종류별 세부 정책, 연차 발생·소멸, 과거 이관 범위는 일부 **실무 확인 필요** 상태다. 확인되지 않은 규칙을 자동 부여·차감 작업의 운영 기본값으로 실행하지 않는다.
- 공휴일 API 동기화, 사용 촉진 자동 메일, PDF·JSON 내보내기, 제품 라이선스는 원본의 후순위 판단을 유지한다. 다만 연차 사용 촉진의 법적·실무 규칙은 나중에 기능을 켤 때 별도로 확인한다.

## 3. 사람, 계정, 인증

### 사원과 역할

- `EMPLOYEE`에는 실제 인원 집계·연차 부여 대상인 사람과 운영용 `SYS_ADMIN` 행이 함께 저장된다. 사원 계정의 역할은 사원, 팀장, 인사 관리자 등으로 관리하고, 인원·휴가 집계에서 `SYS_ADMIN` 행을 제외한다.
- `SYS_ADMIN`은 `EMPLOYEE` 테이블에 저장하는 **운영용 계정 1개**다. 이 행은 이메일·입사일이 없는 비인사 계정으로 사원 수와 연차 대상에서 제외한다. 현재는 활성 계정을 최대 1개로 제한하고, 추가 계정 발급 기능을 두지 않는다.
- 관리자 계정의 담당자를 지정한다. 실제 사원이기도 하면 본인의 휴가는 별도의 사원 계정으로 신청한다. 두 행이 같은 사람이라는 연결 정보는 대표 검토 리포트를 구현하기 전에 추가한다.
- 시스템 관리자는 인사 관리자의 휴가 처리 권한과 시스템 운영 권한을 가진다. 여러 운영자에게 개인별 관리자 계정이 필요해지면 계정 저장 구조와 감사 주체를 함께 재설계한다.
- 최초 관리자 비밀번호를 문서·코드·시드 데이터에 고정하지 않는다. 한 번만 실행되는 초기 발급 절차로 설정하고 첫 로그인 시 변경한다. 유일한 활성 시스템 관리자 계정을 비활성화할 때에는 복구·인계 절차를 먼저 마련한다.
- 관리자 계정 하나를 두 사람이 공유하면 로그에는 계정만 남아 실제 조작자를 판별할 수 없다. 여러 사람이 운영해야 한다면 공유를 시작하기 전에 개인별 계정 방식으로 전환한다.

### 재직 상태와 세션

- `ACTIVE`: 역할에 맞는 신청·확인·승인·관리 기능을 사용할 수 있다.
- `ON_LEAVE`: 로그인과 본인 정보·기록·공지 등의 조회는 가능하다. 신청, 결재, 취소·정정, 정책 변경 같은 업무 상태 변경은 서버에서 차단한다. 휴직 중인 팀장의 대기 결재는 적임자에게 다시 배정하고 알린다.
- `RESIGNED`: 신규 로그인과 기존 세션의 접근을 모두 차단한다. 연결된 시스템 관리자 계정도 회수 또는 비활성화한다.
- 역할·재직 상태·계정 소유자가 바뀌면 관련 세션을 만료하거나 매 요청에서 현재 권한을 확인한다. 화면 숨김만으로 권한을 구현하지 않는다.
- 사원은 사전 등록된 이메일로 Google OAuth와 비밀번호 로그인을 병행한다는 원본 가정을 유지한다. 등록되지 않은 사용자는 거부한다. 시스템 관리자 계정은 별도 고유 로그인 ID와 비밀번호를 사용한다.

## 4. 권한과 개인정보 표시

- 사원은 본인의 사유·신청·잔여·원장을 본다. 팀장은 **현재 자신에게 1차 확인이 배정된 신청**의 사유만 본다. 부서 전체 목록이나 달력에서 팀원의 사유를 읽을 수 없다.
- 인사 관리자와 시스템 관리자는 업무상 필요한 신청 사유를 볼 수 있다. 민감한 사유의 조회도 계정·대상·시각을 감사 기록에 남긴다.
- 회사 전체 달력은 사용자 결정에 따라 연차·반차·병가 같은 **휴가 종류**와 부재 날짜를 표시하고 개인 사유는 표시하지 않는다. 병가·법정휴가 종류 자체가 건강·가족 관련 정보를 드러낼 수 있으므로 공개 범위는 개인정보 담당자가 운영 전에 확인한다.
- API의 조회 범위는 서버에서 판정한다. 특히 상위 부서장에게 넘어간 신청, 팀장 미지정 부서의 신청, 팀장 변경으로 재배정된 신청을 단순한 `내 부서 = 신청자 부서` 조건으로 처리하지 않는다.
- 인사 관리자 본인의 휴가는 본인이 최종 승인할 수 있다. 시스템 관리자도 별도 사원 계정으로 신청한 자신의 휴가를 시스템 관리자 계정으로 처리할 수 있다. 이는 허용된 운영 결정이며, 해당 처리뿐 아니라 **특권 계정 소유자의 휴가·원장 변경 전체**가 대표 검토용 Excel에 포함되어야 한다.

## 5. 핵심 데이터와 불변식

### 권장 데이터 구조

- `EMPLOYEE`: 실제 사원의 부서·입사일·재직 상태와 단일 `SYS_ADMIN` 운영 계정을 함께 저장한다. 시스템 관리자 행에는 입사일·이메일을 두지 않고 사원 수·연차 대상에서 제외한다.
- `EMPLOYEE`의 `SYS_ADMIN` 행: 단일 운영 계정의 로그인 ID, 비밀번호 해시, 활성 상태와 담당자 이름. 일반 사원 행과 역할·필드로 구분하며 별도 관리자 테이블을 두지 않는다. 향후 개인별 계정 전환 시 감사 로그와 실제 사원 계정의 연결 방법을 함께 설계한다.
- `LEAVE_TYPE`: 연차, 오전·오후 반차, 병가, 공가, 경조사, 법정휴가의 분류와 일수 계산·표시 정책.
- `LEAVE_REQUEST`: 신청자, 종류, 원래 신청 기간, 사유, 현재 결재 상태, 현재 결재자, 작성·수정 시각. 상태는 조회 편의를 위한 현재값이며 변경 이력은 감사 기록에 남긴다.
- `LEAVE_REQUEST_DAY`와 점유 슬롯: 실제 휴가 날짜별 기록. 종일 휴가는 오전·오후 두 슬롯을, 반차는 해당 슬롯 하나를 점유한다. 신청 중·승인 중·취소 요청 중에는 점유를 유지한다. 반려·취소·휴일 제외로 해당 슬롯이 해제되면 과거 행은 보존한다. 활성 슬롯에 대한 `(사원, 날짜, 오전/오후)` 중복은 DB 제약으로 막는다.
- `LEAVE_HISTORY`: 연차에 영향을 주는 `GRANT`, `USE`, `REFUND`, `ADJUST`, `EXPIRE`, `CARRY_OUT`, `CARRY_IN`, `IMPORT` 사건을 덧붙인다. 기존 행을 수정·삭제해 잔여를 맞추지 않는다. 휴가 사용·환급은 실제 **휴가 날짜**를 기록하고, 별도로 처리 시각과 대상 기산 기간을 보존한다.
- `LEGAL_LEAVE_PERIOD`: 인사가 등록한 법정휴가·휴직 종류, 시작일, 예정 종료일, 실제 종료일, 상태 및 관련 사원. 휴직 상태로 전환할 종류와 시점은 인사 실무 확인에 따른다.
- `ACTION_LOG`: 실제 행위자 계정 ID, 대상, 작업, 시각, 변경 전후의 필요한 식별값. 사유 원문·비밀번호·불필요한 민감정보를 넣지 않는다.
- `IMPORT_BATCH`, `NOTIFICATION`, `BATCH_RUN`, `BACKUP_MANIFEST`: 이관 원천과 행 상태, 발송 대기·결과, 날짜 작업 성공일, 백업 파일의 시각·해시·검증 결과를 각각 기록한다.

### 생성 시각과 변경 이력

- 이름은 `create_at`이 아니라 **`created_at`**으로 통일한다. 사원·계정·부서·휴가 종류·신청·신청 날짜·법정휴가 기간·정책·공지·첨부파일·이관 배치·알림·날짜 작업·백업 기록 등 상태가 바뀌는 핵심 업무 테이블에는 `created_at`과 `updated_at`을 둔다. 상태가 바뀌는 행에는 `status_changed_at` 또는 그 상태에 맞는 시각도 저장한다.
- 덧붙이기만 하는 `LEAVE_HISTORY`와 `ACTION_LOG`에는 `created_at`을 두고 `updated_at`을 두지 않는다. 승인·반려·취소·정정의 **누가, 언제, 무엇을, 왜**는 `ACTION_LOG`의 행위자 계정 ID, 작업명, 대상 ID, 시각, 필요한 변경 전후 값과 사유 코드로 남긴다. 신청의 현재 상태만 보고 과거 처리자를 추측하지 않는다.
- 휴가를 **사용한 날짜**인 `leave_date` 또는 원장의 `occurred_on`과 **시스템에 기록한 시각**인 `created_at`을 구분한다. 과거 Excel을 오늘 가져오면 `occurred_on`은 과거 휴가일, `created_at`은 오늘 이관 시각이다. 원본 파일에 실제 작성 시각이 있으면 `source_created_at`에 별도 보관하고 시스템 기록 시각을 과거로 덮어쓰지 않는다.
- 신청에는 현재 상태의 변경 시각을 두고, 신청·팀장 확인·최종 승인·취소 요청·취소 완료의 순서는 감사 이벤트에서 복원한다. 관리자 계정의 최초 발급·담당자 인계·비활성화, 사원 재직 상태 변경, 사유 조회, 대표용 Excel 출력, 백업·복원 시도도 각각 시각과 행위자를 남긴다.
- 저장 시각은 서버·DB가 **UTC로 기록**하고 화면과 업무 날짜 계산에서 `Asia/Seoul`로 표시한다. 시각은 초 이하 정밀도까지 저장할 수 있게 하고, 같은 시각에 여러 사건이 생겨도 정렬되도록 단조 증가 ID를 함께 사용한다. `updated_at`의 자동 갱신은 모든 변경 경로에서 일관되게 적용한다.

### 트랜잭션 규칙

1. 같은 사원의 원장·신청·슬롯을 바꾸는 경로는 하나의 잠금 순서를 공유한다. 전사 인원 판단이 필요한 경로는 `POLICY` 행을 먼저, 해당 사원 행을 다음에 잠근 뒤 최신 잔여·겹침·인원을 다시 읽는다. 배치·이관·정정도 예외가 아니다.
2. 승인·환급·정정 등의 업무 변경과 감사 기록 삽입은 같은 DB 트랜잭션에서 성공하거나 함께 롤백된다. 메일 발송은 커밋 후에 별도로 진행한다.
3. 원장에는 작업별 멱등성 키를 둔다. 예: `USE:신청ID:날짜`, `REFUND:신청ID:날짜`, `GRANT:사원ID:기산일`. 환급 사유는 키가 아닌 별도 필드에 둔다. 멱등성 키는 재시도·중복 환급을 막고, 날짜 슬롯 제약은 **서로 다른 신청의 중복**을 막는다.
4. MySQL의 격리 수준과 JPA 읽기 동작을 명시하고 잠금 뒤에 최신 데이터를 읽도록 한다. 이전 스냅샷으로 잔여를 합산하지 않도록 원장 쓰기 트랜잭션의 읽기 방식을 정한다.
5. 승인 후 취소 요청 중인 날짜는 취소가 확정되기 전까지 승인된 휴가와 동일하게 부재·슬롯 점유로 센다.
6. 당겨쓴 연차의 다음 기간 회수는 `CARRY_OUT`·`CARRY_IN`으로 표현한다. Excel의 `소멸` 칸에 음수 소멸을 표시하지 않고 이월 차감을 별도 칸에 표시한다. 세부 연차 정책은 실무 확인 전 운영 작업으로 켜지 않는다.

## 6. 신청·확인·승인·취소

- 일반 신청은 `신청 → 팀장 1차 확인 → 인사 관리자 또는 시스템 관리자 최종 승인` 순서다. 팀장이 없는 부서는 가장 가까운 상위 팀장이 1차 확인한다. 팀장 부재 중에는 신청자가 상위 부서장에게 넘기기를 요청할 수 있다.
- 팀장 본인과 인사팀 사원의 신청은 1차 확인 없이 최종 승인자에게 간다. 자기 결재가 허용된 인사 관리자·시스템 관리자의 처리도 별도 감사·대표 검토 대상이다.
- 신청 시 겹침, 금지 기간, 휴가 종류의 자격과 일수, 연차 한도를 확인한다. **인원 부족은 신청 차단 사유가 아니라 경고**다. 팀장 본인 신청에도 같은 경고를 표시한다.
- 1차 확인 및 최종 승인 시 겹침·잔여·인원 상태를 다시 확인한다. 승인 시 날짜별 `USE` 행과 상태 변경, 감사 기록을 같은 트랜잭션에서 처리한다.
- 팀장 변경·휴직·퇴직 때 미처리 신청의 현재 결재자를 재배정하고 알린다. 사유 조회 권한은 과거 부서 관계가 아니라 **현재 배정된 결재 건**으로 판정한다.
- 대기 중인 신청은 본인이 취소할 수 있다. 승인된 신청의 취소 요청은 최종 승인자가 처리한다. 취소 요청 중에는 해당 날짜가 여전히 승인된 부재다. 승인된 취소에만 날짜별 환급 행을 추가한다.
- 날짜가 지난 미처리 신청은 관리자가 목록에서 확인한다. **이미 닫힌 기산 기간의 뒤늦은 승인은 실무 확인 전 차단**한다. 지난 날짜라도 기간이 아직 열려 있다면 기존 승인 규칙을 적용한다. 반려·취소 및 예외 처리의 사유를 감사 기록에 남긴다.
- 이미 소멸한 기간의 연차를 단순 취소로 되살리지 않는다. 사후 정정이 필요하면 인사가 사유와 근거를 남기는 별도 원장 사건으로 처리한다. 구체적인 예외는 실무 확인 사항이다.

## 7. 최소 잔류 인원

- 인사 관리자는 전사 최소 인원과 팀별 하한을 정한다. 팀장은 자기 팀의 최소 잔류 인원을 하한 이상으로 정하고, 1차 확인 단계에서 팀 기준 부족을 판단한다.
- 신청자에게 날짜별 예상 부재·잔류 인원과 **팀 기준 / 전사 기준** 중 어느 기준이 걸렸는지를 경고한다. 인원 부족이어도 신청 자체는 접수된다.
- 팀장이 통과시킬 수 있는 것은 팀 기준 초과다. 전사 기준 초과 여부는 인사 관리자 또는 시스템 관리자가 최종 승인에서 판단한다. 하나의 `staff_limit_override` 플래그로 두 기준을 함께 우회하지 않는다.
- 최종 승인 직전에 최신 인원으로 재계산한다. 팀장 확인 후 팀 기준이 새로 부족해졌다면 다시 팀장에게 확인을 요청한다. 1차 확인 단계가 없는 팀장 본인·인사팀 신청은 최종 승인자가 경고를 보고 판단한다.
- `APPROVED`와 `CANCEL_REQUESTED`의 유효 날짜를 부재로 센다. `LEADER_OK` 등 대기 건은 경고 화면에 예상 부재로 따로 보여주되 실제 승인된 부재와 구분한다. 법정휴가·휴직은 인원 현황에는 포함하되 최소 인원 규칙을 이유로 등록을 거부하지 않는다.

## 8. 임시공휴일과 날짜별 환급

1. 휴일이 새로 지정되면 해당 날짜를 포함한 대기·승인 신청을 날짜 단위로 찾아 영향 목록을 만든다.
2. 관리자가 영향 목록과 환급 일수를 확인한다. 승인된 연차·반차의 **영향받은 날짜만** `EXCLUDED` 또는 `REFUNDED`로 표시하고 그 날짜의 `REFUND` 행을 한 번만 추가한다. 나머지 신청 날짜와 결재 기록은 유지한다.
3. 대기 중 신청은 계산 일수와 표시를 다시 산정하고, 해당 날짜가 휴가 대상에서 빠졌음을 신청자·결재자에게 알린다. 이미 처리된 날에 대한 환급은 중복 실행해도 원장에 한 번만 반영한다.
4. 같은 날짜의 병가·공가·법정휴가처럼 연차를 차감하지 않는 유형은 종류별 업무 규칙을 확인해 상태를 처리한다. 자동 환급액은 0이며, 인원의 실제 부재 여부는 HR 기록에 따른다.

## 9. 법정휴가·휴직

- 출산전후휴가·육아휴직 등 법정 장기휴가는 경조사 `FAMILY`와 분리한 `LEGAL` 분류로 둔다. 사원의 일반 신청 종류 목록에서는 제외하고 인사가 기간을 등록·정정한다. 직원은 자신의 기록을 볼 수 있다.
- 법정휴가 등록은 일반 팀장 확인이나 최소 잔류 인원 판단으로 거부하지 않는다. 날짜별 인원 현황에는 부재로 반영한다. 이미 승인된 연차와 겹치면 충돌 날짜를 확인하고 그 날짜의 연차를 환급한다.
- 휴직 상태로 관리해야 하는 종류는 HR이 승인한 시작·종료 기간에 따라 `ON_LEAVE`를 적용한다. 휴직 기간 중에도 로그인과 조회는 허용한다.
- 특정 휴가를 일률적으로 ‘90일’로 고정하지 않는다. 법정 일수·분할·시작/종료 제한과 회사 처리 절차는 실무·노무 확인 후 결정한다. 확인 전에는 HR이 날짜와 근거를 등록하며 시스템은 아직 확정되지 않은 일수 규칙으로 임의 반려하지 않는다.

## 10. Excel 이관과 내보내기

- 운영 이관 범위는 **실무 확인 필요**다. 전체 과거 내역을 옮길지, 현재 잔여를 기초 잔액으로 가져올지, 퇴직자·휴직자와 누락된 과거 사용을 어떻게 처리할지 인사 담당자가 정한다.
- 이관은 `파일 업로드 → 형식·사원·날짜·반차 표기 검증 → 행별 오류와 중복 미리보기 → 기준 잔액 대조 → 인사 승인 → 원장 반영` 순서다. 오류 행을 조용히 건너뛰지 않는다.
- 원천 파일 해시, 행 번호와 업무상 고유값을 기록한다. 파일을 다시 올리거나 일부 행을 수정해 재업로드해도 이전에 반영한 사용일이 중복 차감되지 않도록 한다.
- 과거 사용 내역과 부여·소멸은 **날짜 순서와 같은 정책 버전**으로 재구성하거나, 인사가 승인한 기초 잔액 방식으로 처리한다. 사원 등록만으로 과거 `GRANT`·`EXPIRE`를 운영 원장에 먼저 생성하지 않는다.
- 이관 후 사람별 원천 잔액·시스템 잔액·차이·예외 처리 사유를 남기고 인사가 승인한다. 대조가 끝나기 전에는 자동 부여·소멸과 기존 Excel 대체를 진행하지 않는다.
- 일반 리포트는 화면 필터를 따른다. 대표 검토용 리포트는 별도의 고정 기간 양식으로 생성해 인사 관리자와 시스템 관리자 담당자에 연결된 **모든 실제 사원 계정**의 신청, 승인·취소, 대리 등록, `ADJUST` 등 원장 변경을 포함한다. 관리자 담당자와 사원 계정의 연결 정보는 리포트 구현 전에 마련한다. 단순히 `self_approved=true`인 행만 추리지 않는다. 생성자·생성 시각·대상 기간·행 수·원장 합계와 내보내기 이력을 남긴다. 개인 사유는 대표용 기본 양식에서 제외한다.

## 11. 알림·날짜 작업·기술 구성

- 신청·재배정·1차 확인·최종 승인·반려·취소·휴일 환급·대리 처리 시 앱 알림을 업무 트랜잭션에서 발송 대기 상태로 기록한다. 메일 작업자는 커밋된 알림을 선점하고 발송 결과와 실패 횟수를 기록한다. 앱이 커밋 직후 재시작되어도 대기 알림을 다시 찾아 보낼 수 있어야 한다.
- SMTP가 가능하다는 가정 아래 메일을 보낸다. 발송 실패는 신청·승인 자체를 되돌리지 않고 관리자에게 표시한다. 메일에 개인 사유를 불필요하게 넣지 않는다.
- 연차 부여·소멸 날짜 작업은 마지막 성공일을 기준으로 누락된 날짜를 따라잡고, 사원별 멱등성 키와 실패 알림을 사용한다. 정책 미확정 상태에서 운영 원장에 자동 기표하지 않는다.
- 원본의 Java·Spring Boot, Spring Security 세션, MySQL, Flyway, React·TypeScript 기반은 유지한다. 업무 날짜 작업은 앱에서 수행할 수 있지만 **운영 백업은 앱의 정책 `backup_cron`과 분리된 호스트 또는 백업 서비스에서 실행**한다.
- 화면·API의 세부 목록은 원본을 기준으로 하되, 원본의 `ON_LEAVE` 로그인 차단, HR 전용 접근 검사, 웹 복원 API, 전체 취소를 전제로 한 휴일 처리는 이 문서에 맞춰 수정한다. 시스템 관리자는 현재 활성 계정 1개 제약을 유지한다.

## 12. 운영 백업·복원

- 자동 백업은 **첫 운영의 필수 조건**이다. 12시간 간격은 사용자가 제안한 **잠정 주기**다. 예를 들어 01:00·13:00에 실행할 수 있으나 운영 담당자가 허용 가능한 최대 기록 손실 시간을 정해야 최종 주기가 확정된다. 매회 성공하더라도 장애 시 마지막 백업 이후 약 12시간의 변경을 잃을 수 있고, 백업 실패가 누적되면 더 길어진다.
- 일관된 DB 전체 백업을 만들고, 공지 첨부파일처럼 DB에 저장된 자료도 포함한다. 백업 직후 운영 서버 밖 저장소로 복사하고 해시·크기·완료 시각을 검증한다. 백업 실패나 오래된 마지막 성공 시각은 시스템 관리자에게 알린다. 접근 권한과 보관기간을 정한다.
- 이관, 배포, 운영 복원 직전에는 별도 백업을 확보한다. 허용 손실 시간이 12시간보다 짧다면 MySQL binary log 보관이나 더 잦은 백업을 검토한다.
- 개발 환경에서 복구 절차를 준비하고 **운영 데이터와 분리된 환경**에서 복원하여 기동·원장 합계·첨부파일을 확인한다. 운영 서버에서 복원 시험이 가능한지는 미정이며, 운영 DB를 덮어쓰며 연습하지 않는다.
- 운영 복원은 운영자가 변경 중지, 대상 백업·해시 확인, 외부 복원 의도 기록, 새 DB/볼륨에 복원, 데이터 대조, 전환 승인 순서로 수행한다. 웹의 `POST /api/admin/backups/{id}/restore` 기능은 첫 운영에 넣지 않는다. 복구 절차와 담당자를 문서화한다.

## 13. 감사 기록과 삭제 불가 요구

- 요구사항: **일반 사용자·관리자·시스템 관리자가 앱에서 원장 및 감사 로그를 삭제하거나 과거 행을 수정할 수 없어야 한다.** 정정은 새 사건을 덧붙이고 원래 사건과 연결한다.
- 앱의 DB 계정에는 원장·감사 테이블에 필요한 조회·삽입 권한만 부여한다. 스키마 변경용 Flyway 계정과 운영 DB 관리자 권한을 분리한다. 삭제·수정 API와 직접 SQL을 실행하는 관리자 화면은 두지 않는다.
- 승인·취소·정정·역할 변경·시스템 관리자 최초 발급·인계·사유 조회·리포트 출력·백업·복원 시도를 행위자 계정과 함께 기록한다. 로그 세부 내용에 신청 사유 원문을 복제하지 않는다. 단일 관리자 계정을 여러 사람이 공유하면 로그만으로 실제 사람을 식별할 수 없다는 한계를 운영 문서에 명시한다.
- DB/서버 최고 권한자가 같은 저장소와 백업까지 통제하면 로컬 `append-only`만으로 ‘그 누구도 삭제 불가’를 보장할 수 없다. 외부의 변경 불가 또는 삭제 탐지 가능한 사본과 **독립된 관리자**가 필요한지 인프라 담당자가 확인한다. 마련되기 전에는 보장 수준을 ‘앱에서 삭제 불가, 외부 사본으로 변조 탐지 가능 여부 미정’으로 정확히 표시한다.
- 복원은 과거 DB로 돌아가 로컬 감사 기록도 사라질 수 있으므로, 복원 의도와 결과를 외부 기록에 먼저 남긴다. 감사 기록의 보존기간과 법정 파기·분리보관 방식은 개인정보 담당자와 정한다. ‘영구 보관’을 무조건 기본값으로 두지 않는다.

## 14. 남은 확인 사항과 담당

### 인사 실무 확인 필요

- 기존 Excel에서 옮길 대상·기간·기초 잔액과 대조 승인자.
- 연차 부여·소멸·당겨쓰기·출근율·사용 촉진·퇴직 정산의 실제 회사 규칙. 확인 전 자동 기표 금지.
- 닫힌 기산 기간의 신청을 뒤늦게 승인할 수 있는지와 예외 정정 방법. 확인 전 닫힌 기간 승인은 차단.
- 인사 관리자 부재 시 대행·권한 회수·복귀 절차. 담당 과장님이 평소 인사 관리자 역할을 맡는다.
- 원본에 남아 있는 병가·공가 노출 조건, 경조사 기간·증빙, 장기근속 포상휴가 기본 규칙.

### 운영·인프라 확인 필요

- 허용 가능한 최대 기록 손실 시간과 복구 목표 시간, 12시간 백업 주기의 적정성.
- 운영 서버 밖 백업 저장소, 분리 복원 환경, 운영 백업·복구 담당자, 실패 알림 수신자.
- 외부 감사 기록 저장소와 독립 관리자 가능 여부. 단일 시스템 관리자 계정의 초기 발급·인계·회수 절차와 담당자 부재 대응.
- Google OAuth·회사 SMTP·공휴일 API의 운영망 접근 가능 여부.

### 노무·개인정보 확인 필요

- 법정휴가·휴직의 종류별 기간, 분할·변경·종료 규칙과 회사 절차.
- 병가 등 휴가 종류의 회사 전체 달력 공개 범위, 사유 조회 기록, 감사 기록과 백업의 보존·파기 기간.

## 15. 원본과 달라진 결정 요약

- 시스템 관리자 계정은 현재 `EMPLOYEE`의 `SYS_ADMIN` 행 하나로 운영한다. 별도 관리자 테이블과 개인별 추가 발급은 여러 운영자에게 계정이 필요해질 때 재검토한다.
- 휴직자 로그인 거부 → 로그인·조회 허용, 업무 변경 차단. 퇴직자는 로그인 거부.
- HR 전용 원장 변경 → HR과 시스템 관리자가 동일한 휴가 처리 권한. 시스템 관리자 추가 발급 기능은 현재 두지 않는다.
- HR 자기 승인 금지 전제 → 자기 승인 허용, 대표 검토용 고정 Excel에 모든 특권 사용자 관련 변경 표시.
- 인원 부족으로 신청 차단 가능 → 경고 후 접수, 팀·전사 판단 권한 분리, 최종 승인 재검사.
- 임시공휴일 발생 시 전체 취소·재신청 → 영향받은 날짜만 환급.
- 출산전후휴가를 `FAMILY` 90일로 고정 → `LEGAL` 분리, 인사 기간 등록, 세부 법정 규칙 확인.
- 백업 후순위·웹 복원 → 운영 전 백업과 분리 복원 검증 필수, 운영자 절차로 복원.
- 원장과 로그를 단순 `append-only`로 선언 → 수정·삭제 경로와 DB 권한 제한, 외부 감사 사본의 관리 가능 여부 확인.
- 닫힌 기간 뒤늦은 승인 선택지 → 실무 확인 전 차단. 열린 기간의 지난 날짜는 기존 처리 규칙 적용.
