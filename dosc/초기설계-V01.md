## 1. 목적과 운영 전제

엑셀·메일·슬랙으로 나뉜 휴가 신청을 시스템 하나로 통합한다. 사원은 신청만 하고, 시스템이 결재 알림·결과 통지·잔여 연차 계산을 처리한다. 관리자가 연차를 수기로 차감하지 않는 것이 성공 기준이다.

- 약 50명이 사용하는 사내 내부망 서비스이며, 서버 한 대를 전제로 한다.
- 1인 개발이며 기한은 정하지 않았다. 먼저 MVP 범위를 고정한다.
- 기존 엑셀은 한 번 이관하고, 이후 시스템을 유일한 원본으로 삼는다.
- 모든 목록 조회는 20건 단위로 페이지네이션한다. 로그를 포함한 전체 목록 일괄 로드는 하지 않는다.
- 연차 계산의 정합성, 개인이 유지할 수 있는 복잡도, 내부망 배포 용이성을 우선한다.
- 인증의 세부 방식과 외부 SMTP·공공데이터 API 접근 가능 여부는 배포 전에 확인한다.

## 4. 기술 구성

| 영역 | 선택 | 사용 목적 |
| --- | --- | --- |
| 백엔드 | Java 21, Spring Boot 4.1.1 | 업무 API와 트랜잭션 처리 |
| 데이터 접근 | Spring Data JPA + 네이티브 SQL | CRUD는 JPA, 리포트·부서 재귀 CTE는 SQL |
| 인증 | Spring Security 세션 | 서버 한 대를 전제로 한 세션 인증 |
| 메일 | Spring Mail + Thymeleaf | 메일 발송·템플릿 |
| 정기 작업 | Spring `@Scheduled` + 실행 로그 | 부여·소멸·촉진·동기화·백업 |
| API 문서 | springdoc-openapi | Swagger UI |
| 엑셀 | Apache POI | 임포트·내보내기 |
| DB | MySQL 8 | 원장·업무 데이터와 잠금 기반 동시성 제어 |
| 스키마 관리 | Flyway, `flyway-core`·`flyway-mysql` | 스키마 변경 이력 관리 |
| 프런트엔드 | React + Vite + TypeScript | 화면 구성, 정적 빌드는 Spring에서 제공 |
| 서버 상태 | TanStack Query | 서버 상태 캐시, 30초~1분 폴링, 처리 후 데이터 갱신 |
| 배포 | Docker Compose | 앱 + MySQL, DB 볼륨은 호스트 경로 |

- Redis 등 서버 캐시, 메시지큐, JWT, Quartz는 도입하지 않는다.
- 앱 내 핵심 정합성은 DB 트랜잭션·행 잠금·유일성 제약으로 보장한다.
- 개발 메일은 개인 Gmail, 배포 메일은 회사 SMTP를 사용하며 SPF/DKIM 설정을 확인한다.
- Flyway는 상위 페이지에 “백업용”으로 적혀 있으나, 상세 문서에서는 스키마 이력 관리 도구다. DB 백업은 별도의 `mysqldump`로 구분한다.

세션 저장 위치(톰캣 메모리 또는 Spring Session JDBC), 만료 시간, 자체 비밀번호 또는 사내 계정 연동 여부는 아직 정하지 않았다.

## 5. 연차와 휴가 정책

### 5.1 원장 중심 계산

```text
잔여 연차 = 해당 사원의 LEAVE_HISTORY.days 합계
원장 유형 = GRANT / USE / CANCEL / ADJUST / EXPIRE
```

- 별도의 잔여 컬럼을 두지 않는다. 원장에 부여·사용·취소·정정·소멸을 기록한다.
- 일수는 반차까지 표현하는 `DECIMAL(4,1)`을 기준으로 한다.
- 신청에는 계산된 일수를 스냅샷으로 저장한다.
- 사용 차감은 관리자 최종 승인 시점에만 한다. 차감 일수가 0인 휴가에는 사용 차감 행을 만들지 않는다.
- 승인 전 반려·취소는 잔여에 영향을 주지 않는다. 이미 차감된 휴가의 취소 승인은 취소 원장으로 돌려준다.
- 대기 신청은 원장 잔여에서 차감하지 않고 대기 건수를 안내한다. 별도 가용 잔여 표시 여부는 미결이다.
- 잔여 부족 시 승인을 거부한다. 당겨쓰기는 확정되지 않았다.

### 5.2 부여·소멸

아래는 원문에 기재된 업무 규칙을 정리한 것으로, 법률 적합성을 별도로 검증한 내용은 아니다.

- 입사일 기준으로 부여한다.
- 1년 미만은 월 1일, 최대 11일이며 입사 1년 시 미사용분을 소멸시킨다.
- 1년 이상은 15일, 원문 표현으로 3년차부터 2년마다 1일 가산하며 최대 25일이다.
- 이월하지 않고 기산일에 미사용분을 `EXPIRE` 음수 행으로 기록한다.
- 결근·출근율 데이터가 없어 자동 부여 후 예외를 관리자 정정으로 처리하는 방향이며, 회사 정책 확인이 필요하다.
- `grant_basis`에는 `HIRE_DATE / FISCAL_YEAR`를 표현하되, MVP 로직은 입사일 기준만 구현한다. 회계연도 전환 계산은 제외한다.

### 5.3 휴가 종류

| 코드 | 명칭 | 차감 단위 | 노출·기간 조건 | 최소 잔류 인원 제한 |
| --- | --- | --- | --- | --- |
| `ANNUAL` | 연차 | 근무일당 1일 | 기간 신청 | 적용 |
| `HALF_AM` | 오전 반차 | 0.5일 | 하루 신청만 허용 | 제외 |
| `HALF_PM` | 오후 반차 | 0.5일 | 하루 신청만 허용 | 제외 |
| `SICK` | 병가 | 0일 | 잔여 0일일 때만 노출 | 제외 |
| `OFFICIAL` | 공가 | 0일 | 잔여 0일일 때만 노출 | 제외 |
| `FAMILY_EVENT` | 경조사 | 0일 | 별도 노출 조건 미기재 | 적용 |

주말·공휴일을 제외하여 일수를 계산한다. 사내휴일은 휴일 테이블에서 관리하되, 종류별 계산 처리의 세부 기준은 구현 전에 정한다. 공휴일·사내휴일·신청 금지 기간을 신청 달력에 표시하고, 신청 금지 기간은 서버에서 신청 자체를 거부한다.

## 6. 신청·결재·취소

### 6.1 고정 결재선

일반 흐름은 **사원 신청 → 팀장 1차 확인 → 관리자 최종 승인**이다. 휴가 종류별 결재선이나 팀장 단계 on/off 정책은 두지 않는다.

| 조건 | 1차 처리 |
| --- | --- |
| 일반 사원 신청 | 직속 팀장이 확인·반려 |
| 팀장이 당일 연차·반차 승인 상태 | 상위 부서장이 대행 |
| 부서 팀장 미지정 | 상위 부서장이 대행 |
| 팀장 본인 신청 | 1차 확인 없이 관리자에게 직접 전달 |
| 팀장이 계속 확인하지 않음 | 사원 또는 관리자가 수동으로 상위에 올림 |

외근은 팀장 부재로 보지 않는다. 관리자 최종 승인은 모든 신청이 거친다.

### 6.2 상태와 전이

| 상태 | 의미 | 다음 처리 |
| --- | --- | --- |
| `PENDING` | 신청 후 대기 | 본인 취소, 1차 확인, 반려 |
| `LEADER_OK` | 팀장 또는 상위 부서장 확인 완료 | 관리자 승인·반려 |
| `APPROVED` | 최종 승인 | 사원 취소요청 또는 관리자 직접 취소 |
| `REJECTED` | 반려 | 종료 |
| `CANCELED` | 승인 전 본인 취소 | 종료 |
| `CANCEL_REQUESTED` | 승인 건 취소요청 대기 | 관리자 취소 승인·거절 |
| `CANCELED_DONE` | 승인 건 취소 완료 | 종료 |

- 팀장확인과 상위확인을 서로 다른 DB 상태로 나누지 않는다. 원문은 `escalated_to`로 상위 확인자를 구분한다.
- 관리자 승인 시 차감 대상 휴가의 `USE` 음수 행을 만든다.
- 취소요청 자체로 잔여를 복구하지 않는다. 관리자 취소 승인 시 `CANCEL` 양수 행을 만든다.
- 취소요청 거절 시 `APPROVED`로 돌아간다.
- 관리자 직접 취소와 대리 등록·삭제도 사원에게 앱 알림·메일을 보낸다.
- 모든 업무 상태 변화는 이벤트로그에 기록한다.

팀장 본인 신청의 관리자 대기를 어떤 상태값으로 표현할지, `LEADER_OK` 이후에도 본인 취소를 허용할지는 원문에 명확하지 않다.

### 6.3 최소 잔류 인원

- 부서별 `min_staff_on_duty`로 관리하며, 0이면 제한하지 않는다.
- 직속 부서의 활성 사원만 모수로 센다. 하위 부서를 합산하지 않는다.
- 연차·경조사에 적용하고 반차·병가·공가는 제외한다.
- 원문은 승인 휴가와 대기 신청을 함께 세며, 화면에서는 `휴가 2명 + 대기 1명`처럼 구분한다.
- 신청 단계에서는 경고만 표시한다. 팀장이 초과를 허용하면 `staff_limit_override`를 남긴다.
- 관리자는 해당 플래그가 있을 때만 제한 초과 승인을 할 수 있다.
- 승인 트랜잭션에서 부서 행을 잠그고 신청 기간의 근무일별로 검사한다.

```text
(활성 팀원 수 − 기존 휴가 인원 − 신청자 1명) < 최소 잔류 인원
→ 제한 초과: 팀장 통과 플래그가 없으면 승인 거부
```

본인 신청의 중복 집계 방지, 동일인의 여러 신청 집계 방식, 취소요청 상태의 포함 여부 등은 상세 구현에서 정의해야 한다.

## 7. 데이터 모델

아래는 원문의 논리 모델이다. 최종 DDL·전체 인덱스·필수값·외래키 삭제 정책은 확정 전이다.

| 테이블 | 주요 필드 | 핵심 규칙 |
| --- | --- | --- |
| `DEPARTMENT` | `id`, `name`, `parent_id`, `leader_id`, `min_staff_on_duty` | 자기 참조 계층, 깊이 제한 없음, 하위 조회는 재귀 CTE |
| `EMPLOYEE` | `id`, `name`, `email`, `hire_date`, `role`, `department_id`, `active` | 사번 미사용, 퇴사자는 삭제 대신 비활성화 |
| `LEAVE_TYPE` | `code`, `name`, `deduct_days`, `only_when_empty`, `staff_limit_applied` | 휴가 코드·차감·노출·잔류 규칙 설정 |
| `LEAVE_REQUEST` | `id`, `employee_id`, `leave_type_code`, `start_date`, `end_date`, `days`, `reason`, `status`, `staff_limit_override`, `escalated_to` | 신청 현재 상태와 일수 스냅샷 |
| `LEAVE_HISTORY` | `id`, `employee_id`, `type`, `days`, `occurred_on`, `request_id`, `source`, `memo` | 잔여 계산의 기준, 출처는 `SYSTEM / ADMIN / EXCEL_IMPORT` |
| `HOLIDAY` | `id`, `start_date`, `end_date`, `name`, `type` | `PUBLIC / COMPANY / BLOCKED`, 하루도 기간으로 표현 |
| `NOTIFICATION` | `id`, `receiver_id`, `type`, `request_id`, `read`, `mail_sent`, `mail_sent_at` | 수신자별 읽음·메일 상태 |
| `ACTION_LOG` | `id`, `actor_id`, `action`, `target_type`, `target_id`, `created_at`, `detail` | append-only, 시스템 행위자는 NULL, 상세는 JSON |
| `POLICY` | `id`, `grant_basis`, `promote_enabled`, `promote_months`, `backup_enabled`, `backup_cron` | 컬럼 기반 단일 행 설정 |
| `NOTICE` | `id`, `title`, `content`, `author_id`, `type`, `published`, `pinned`, `created_at`, `updated_at` | 수동·시스템 공지, 초안·발송·상단 고정 |

### 관계와 제약

- 부서는 여러 사원을 가지며, 사원은 여러 신청·원장·알림·행위 로그와 연결된다.
- 신청은 하나의 휴가 종류를 참조한다. 원장은 신청에서 발생한 경우 `request_id`로 연결하고 부여 등은 NULL일 수 있다.
- 원장에 `UNIQUE(request_id, type)`을 두어 같은 신청의 같은 유형 처리가 중복되지 않게 한다.
- 원장 조회 인덱스는 `(employee_id, occurred_on)`이다.
- 로그 인덱스는 `(target_type, target_id, created_at)`, `(actor_id, created_at)`, `(created_at)`이다.
- 상태·행위 enum은 문자열로 저장하며 `ORDINAL`을 사용하지 않는다.
- 정책 컬럼 추가는 Flyway로 관리하고, 기존 단일 행을 고려해 필수 컬럼에는 `NOT NULL DEFAULT`를 지정한다.
- 휴일·정책은 특정 사원이나 신청에 종속되지 않는다.

원문 ERD의 신청-원장 관계는 0..1로 그려져 있으나 사용과 취소를 모두 기록하면 한 신청에 여러 유형의 원장이 생긴다. 관계 확정 전 이 불일치를 수정해야 한다. 공지 알림의 참조 필드와 스케줄러 실행 로그 테이블도 아직 상세 모델에 없다.

## 8. 정합성과 트랜잭션

| 대상 | 원문 설계 방향 |
| --- | --- |
| 승인·차감 | 업무 처리를 트랜잭션으로 묶고, 잔여 부족 검증 후 원장 기록 |
| 중복 승인·차감 | 조건부 UPDATE, 행 잠금, 원장 `UNIQUE(request_id, type)` 조합 |
| 신청 기간 중복 | 사원 행 잠금 → 겹침 조회 → 신청 삽입을 한 트랜잭션으로 처리 |
| 잔류 인원 | 승인 트랜잭션 안에서 부서 행을 잠그고 근무일별 검증 |
| 업무 로그 | 업무 변경과 같은 트랜잭션에 기록, 독립 `REQUIRES_NEW` 기록은 하지 않음 |
| 외부 메일 | 커밋 후 비동기 발송, 실패 시 재시도 |

MySQL의 기간 겹침 제약 부재를 사원 행 잠금으로 보완한다. 구체적인 잠금 획득 순서·조건부 갱신 조건·재시도 규칙은 아직 확정되지 않았다.

## 9. 알림·공지·이벤트로그

### 9.1 알림과 메일

- 신청접수, 1차 확인, 승인·반려, 취소요청·취소완료, 대리 등록·삭제를 알린다.
- 수신 순서는 팀장 또는 상위 부서장 → 1차 확인 후 관리자이며, 신청자는 처리 결과를 받는다.
- 메일 본문에 웹 결재 화면 링크를 포함한다.
- 알림 행을 저장하고 `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`로 메일을 보낸다. 실패 시 재시도하며 결과를 알림 행에 기록한다.
- 화면은 30초~1분 폴링한다. 본인 요청 결과는 응답 직후 반영한다.
- 취소요청 접수·백업 실패 등 관리자 전용 알림은 정책에서 선택하는 방향이다. 해당 정책 필드는 추가 설계가 필요하다.
- 촉진 메일은 소멸 N개월 전에 자동 발송하거나 관리자가 개별 발송한다. MVP 후순위다.

### 9.2 공지사항

- `MANUAL`은 관리자 작성, `SYSTEM`은 정책 변경에 따른 자동 생성이다.
- 자동 생성 공지는 `published=false` 초안으로 저장한다.
- 관리자가 내용을 확인한 뒤 “저장 후 발송”하면 게시하고 알림을 생성한다.
- 사원에게는 게시된 공지만 보여주고, 관리자에게 미발송 공지 건수를 표시한다.
- 중복 발송을 막도록 게시 여부를 검사한다. 발송된 공지를 수정해도 재발송하지 않는다.
- 공지와 알림 행 저장은 트랜잭션으로 처리하되 실제 메일은 커밋 이후에 보낸다.
- 정책 변경 전후 값은 로그 `detail`을 활용한다. 사용자에게는 내부 필드명 대신 표시용 이름을 보여준다.

| 정책 필드 | 표시 이름 | 자동 공지 |
| --- | --- | --- |
| `grant_basis` | 연차 부여 기준 | 대상 |
| `promote_months` | 연차 사용 촉진 안내 시점 | 대상 |
| `backup_cron`, `backup_enabled` | 운영 백업 설정 | 제외 |

### 9.3 이벤트로그

| 구분 | action |
| --- | --- |
| 신청 | `APPLY`, `PROXY_APPLY`, `LEADER_CONFIRM`, `APPROVE`, `REJECT`, `SELF_CANCEL`, `CANCEL_REQUEST`, `CANCEL_APPROVE`, `CANCEL_REJECT` |
| 연차 변동 | `GRANT`, `EXPIRE`, `ADJUST`, `EXCEL_IMPORT` |
| 사원 | `EMPLOYEE_CREATE`, `EMPLOYEE_UPDATE`, `EMPLOYEE_DEACTIVATE`, `DEPARTMENT_CHANGE`, `ROLE_CHANGE` |
| 설정 | `POLICY_CHANGE`, `HOLIDAY_ADD`, `HOLIDAY_DELETE`, `LEAVE_TYPE_CHANGE` |
| 공지 | `NOTICE_CREATE`, `NOTICE_UPDATE`, `NOTICE_DELETE` |
| 알림 | `NOTIFY_SENT`, `MAIL_SENT`, `MAIL_FAILED`, `NOTIFY_READ` |
| 배치 | `BATCH_FAILED` |

총 30종이다. 로그인·로그아웃은 현재 제외하며 보안 감사 요구가 생기면 재검토한다. 배치 성공 자체는 이벤트로그에 매번 남기지 않되, 부여·소멸 업무 결과는 사원마다 기록한다.

부서 변경 상세에는 부서 ID와 이름을 함께 남긴다. 알림 테이블은 현재 상태, 로그는 발송·재발송 등 시간별 이력을 담당한다. JSON 상세의 전문 검색은 범위에서 제외하고 자주 검색하는 값은 필요할 때 별도 컬럼으로 분리한다.

출처: 하위 문서 6·7장.

## 10. 엑셀 이관과 리포트

### 이관

1. 기존 엑셀의 하루 한 행 데이터를 읽는다.
2. `(*)`가 있으면 0.5일, 없으면 1일 사용으로 해석한다. 표시는 위치와 무관하게 제거한 뒤 날짜를 파싱한다.
3. 파싱 오류 행을 모아 사용자에게 보여준다. 오류를 조용히 건너뛰지 않는다.
4. 사용 내역은 `USE` 음수 원장, 출처 `EXCEL_IMPORT`로 저장한다.
5. 입사일 기준 부여분을 계산해 `GRANT` 양수 원장을 만든다.
6. `사원 | 엑셀 잔여 | 시스템 계산 잔여 | 차이`로 대조한다.

과거 이력 화면을 위해 승인 완료 신청도 만들지는 미결이다. 동일 파일 재이관 방지 방식도 상세 설계가 필요하다.

### 리포트

- 전체·부서·사원·기간 조건으로 조회·다운로드한다.
- 조회 화면과 같은 필터·쿼리를 사용한다.
- 기본 열은 `부서 | 이름 | 사용일자 | 종류 | 일수 | 잔여`다.
- 본문 기준 기간 신청은 날짜별 한 행으로 출력하지만, 미결 목록에서는 신청 단위 출력도 검토 중이다.
- 반차의 `(*)` 표시는 엑셀 출력에만 사용한다. 예: `2026-09-17 (*)`.
- 엑셀 파일은 현황 리포트이며 DB 백업을 대체하지 않는다.

출처: 하위 문서 8·9·13장.

## 11. 스케줄러·백업·배포

- 자동 작업은 연차 부여·소멸, 촉진 메일, 공휴일 동기화, DB 백업이다.
- Spring `@Scheduled`와 실행 로그를 사용하며, 미실행 소멸분 보정이 필요하다.
- DB 전체를 `mysqldump`로 백업한다. 정책 주기 자동 실행과 관리자 수동 실행을 설계한다.
- 복원은 관리자 화면의 파일 선택·확인 단계·로그 기록을 거친다.
- 백업 파일은 DB와 다른 디스크에 저장한다. 복구 절차를 실제로 한 번 이상 검증한다.
- React 정적 빌드를 Spring이 제공하여 앱 배포 단위를 하나로 구성한다.
- Docker Compose로 앱과 MySQL을 실행하고 DB 데이터는 호스트 경로에 보존한다.
- 내부망에서 SMTP와 공공데이터 API 호출이 가능한지 확인한다.

백업·복원 제품 기능과 공휴일 API 동기화는 MVP 후순위다. 정기 작업의 실행 로그 스키마, 중복 실행 방지, 재기동 시 누락분 처리 범위는 추가 설계 대상이다.

## 12. API 공통 응답

상위 페이지에 정의된 공통 응답 형태를 따른다. 아래 실패 예시의 400과 문구는 형식을 설명하기 위한 예시이며, 실제 상태 코드 매핑은 미정이다. 원문의 누락된 쉼표를 보완해 유효한 JSON으로 작성했다.

성공:

```json
{
  "success": true,
  "data": {}
}
```

실패:

```json
{
  "success": false,
  "error": {
    "status": 400,
    "message": "요청을 처리할 수 없습니다."
  }
}
```

엔드포인트 목록, HTTP 메서드, 요청·응답 DTO, 페이지네이션 메타데이터, 오류 코드 목록은 원문에 없다. 후속 API 설계에서 정의한다.

| 고정 결재선 | 휴가 종류마다 결재 정책을 늘리지 않고 잔류 인원 예외 판단 주체를 명확히 함 |
| 휴가 규칙은 제한된 코드·필드로 표현 | 자유형 규칙 엔진의 복잡도 방지 |
| 오전·오후 반차를 종류로 구분 | 오늘 휴가 인원 화면에서 시간대 표시 |
| 입사일 기준만 MVP 구현 | 회계연도 전환·비례 계산·정산의 범위 확대 방지 |
| 세션 인증 | 단일 서버 운영에서 토큰 발급·갱신 체계의 추가 구현을 피함 |
| 서버 캐시·메시지큐 미도입 | 현재 요구사항은 DB 잠금과 메일 비동기로 처리 |
| 퇴사자 비활성화 | 기존 신청·원장·이력 보존 |
| 정책은 단일 행·타입별 컬럼 | 설정 타입을 명확히 하고 Flyway로 변경 관리 |

세션을 쓴다는 사실만으로 역할 변경·퇴사 처리가 기존 로그인에 자동 반영된다고 확정하지 않는다. 실제 반영 방식은 인증 상세 설계에서 검증해야 한다.

출처: 하위 문서 4·5·12장. 마지막 문장은 구현 시 확인 사항이다.

## 14. 미결 사항과 원문 불일치

## 15. 후속 설계 순서 제안

아래 순서는 원문의 확정 일정이 아니라, 이 문서를 기준으로 개발을 시작하기 위한 제안이다.

1. 미결 사항 중 결재 상태·취소·휴가 계산·권한 범위·인증 수단을 먼저 결정한다.
2. 원장 정합성 제약, 잠금 순서, 필수값과 인덱스를 확정하고 Flyway 스키마를 작성한다.
3. 역할별 조회 범위와 API·DTO·오류·페이지 응답 계약을 정한다.
4. 신청 → 1차 확인 → 최종 승인 → 원장 차감의 핵심 흐름을 구현한다.
5. 동시 승인, 중복 요청, 기간 중복, 잔여 부족, 반차, 취소 복구를 검증한다.
6. 알림·메일, 엑셀 이관·잔액 대조, 리포트를 연결한다.
7. 회사 정책·내부망 통신·운영 백업을 확인한 뒤 초기 배포 범위를 확정한다.
