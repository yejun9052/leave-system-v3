### 이번 V02 갱신 (2026-09-21 16:22 KST 원문 기준)

- 운영 Google OAuth 2.0, 개발 dev 폼 로그인, 공통 이메일 기반 사원 조회·세션을 명시했다. EMPLOYEE에 비밀번호를 저장하지 않는다.
- USE·CANCEL을 날짜당 한 행으로 저장하고 키에 날짜를 포함한다. 신청-이력 ERD는 1:N으로 수정됐다.
- NOTICE_FILE 7개 필드, LEAVE_TYPE 4개 필드, LEAVE_REQUEST.leader_confirmed_by가 추가되어 **11개 테이블·84개 컬럼**이다.
- 역할별 API 목록과 preview·신청·팀장 확인·인사 승인 계약, 기산일 걸침 거부, 본인 신청의 LEADER_OK 초기 상태가 추가됐다.
- 경조사 사유별 종류·근속 제한·서버 종료일 계산, 공지 첨부, 날짜 지난 미처리 목록, 복원 절차를 구체화했다.
- 취소요청·공지 첨부·미처리 목록은 MVP 포함으로 변경됐다. 휴일 변경 복구는 전체 취소·CANCEL 경로로 정리됐다.

## 2. 목적·운영 전제·기술

약 50명이 사용하는 사내 내부망 서비스로, 엑셀·메일·슬랙에 흩어진 신청과 수기 차감을 통합한다. 1인 개발이며 시스템을 1회 엑셀 이관 후 유일한 원본으로 삼는다. 목록은 20건 페이지네이션한다.

| 영역 | 선택 |
| --- | --- |
| 서버 | Java 21, Spring Boot 4.1.1 |
| 저장·조회 | MySQL 8, Spring Data JPA, 리포트·부서 재귀 CTE만 네이티브 SQL |
| 스키마 | Flyway |
| 인증 | Spring Security 세션 + OAuth2 Client, 운영 Google OAuth / 개발 폼 로그인 |
| 메일 | Spring Mail + Thymeleaf |
| 자동 작업 | Spring @Scheduled + 실행 로그 |
| API·엑셀 | springdoc-openapi, Apache POI |
| 화면 | React + Vite + TypeScript, TanStack Query |
| 배포 | Spring이 프런트 정적 빌드 제공, Docker Compose 앱 + MySQL, 호스트 DB 볼륨 |

Redis 등 서버 캐시·메시지큐·JWT·Quartz는 도입하지 않는다. 상위 페이지의 Flyway '백업용' 표현과 별개로 상세 설계의 DB 전체 백업은 mysqldump다.

### 인증·세션

- 운영은 Google Workspace 계정으로 Google OAuth 2.0 로그인, 이후 요청은 세션을 사용한다.
- 이메일로 사전 등록된 EMPLOYEE를 조회해 역할을 부여한다. 미등록 이메일과 회사 도메인 외 계정은 거부하며 퇴사자는 비활성화한다.
- EMPLOYEE에 비밀번호 컬럼을 두지 않고 비밀번호 변경·재설정 기능도 제공하지 않는다.
- 개발은 dev 프로필 전용 폼 로그인이다. 원문의 테스트 계정 표기는 hr@, admin@, leader@, member@test.local이며 앞 세 주소의 도메인은 생략되어 있다. EMPLOYEE는 Flyway dev 시드, 비밀번호는 dev 인메모리 설정에 둔다.
- 폼 로그인 설정은 @Profile("dev")로 제한하고 prod에서는 켜지지 않아야 한다.
- 세션 저장소(톰캣 메모리 / spring-session-jdbc)와 만료 시간은 여전히 미정이다. 기존 코드의 세션 시간은 Notion 확정값으로 간주하지 않는다.
- 외부 Google OAuth 허용 여부는 회사 IT 확인 사항이다. 이전 SMTP/API 허용 체크는 최신 질문 목록에서 빠졌으며 구체 접속 설정은 없다.
- 원문은 권한 변경·퇴사의 즉시 반영을 목표로 하지만, 기존 세션을 무효화하거나 사원 상태를 재검증하는 방법은 아직 정의하지 않았다.

## 3. 권한·결재

| 역할 | 코드 | 범위 |
| --- | --- | --- |
| 사원 | MEMBER | 본인 신청·대기 취소·취소요청·잔여·이력, 공지·알림·팀 현황·전체 캘린더 |
| 팀장 | LEADER | 사원 기능 + 팀 신청 1차 확인·반려, 잔류 인원 초과 판단, 하한 이상 팀 최소 인원 설정 |
| 시스템 관리자 | SYS_ADMIN | 팀장 메뉴 상속 + 계정·부서·휴일·운영 백업 정책·백업/복원·리포트·로그 |
| 인사 관리자 | HR_ADMIN | 시스템 관리자 권한 + 최종 승인·반려·취소·정정·대리 등록/삭제·엑셀 이관·연차 정책·휴가종류·인사 역할 부여 |

사람이 수동으로 잔여를 바꾸는 경로는 인사 관리자만 호출한다. 원장 INSERT를 서비스 한 곳에 모으는 방향이다. 시스템 관리자는 자신에게 인사 관리자 역할을 줄 수 없다. 단일 role 컬럼을 유지한다. 자동 GRANT·EXPIRE는 시스템이 수행한다.

일반 결재선은 **사원 → 팀장 또는 상위 부서장 확인 → 인사 관리자 승인**이다. 모든 휴가 종류에 동일하게 적용하고 팀장 단계 on/off는 두지 않는다.

- PENDING은 팀장 화면, LEADER_OK부터 인사 관리자 화면에 표시한다.
- 팀장·인사 관리자 본인 신청은 1차 확인을 생략하고 LEADER_OK로 저장한다. 인사 최종 승인은 동일하게 거친다.
- 인사 관리자 본인 신청은 1차 확인 없이 스스로 최종 승인·반려한다. 일반 잔여·금지 기간·잔류 인원 검증은 유지하고 ACTION_LOG.detail에 `"self": true`를 남긴다.
- 팀장 승인 휴가(연차·반차·병가·공가·경조사)는 자동 상위 전달 사유다.
- 출장·교육·급한 결근은 사원 또는 관리자가 수동 에스컬레이션한다. 외근·재택은 부재가 아니다.
- 병가·공가도 현재는 팀장 확인 → 인사 승인이다. 팀장만으로 종료할지는 미결이다.
- 사유 조회는 본인 신청 상세·팀장 확인·인사 화면으로 제한한다. 소속·권한 조건은 서버가 강제한다.
- 1차 확인 시 leader_confirmed_by에 실제 처리자를 남긴다. 상위 확인자는 escalated_to로 권한을 판정한다.
- 팀장 판정은 DEPARTMENT.leader_id를 기준으로 role이 따라가도록 보완하는 방향이며, 상세 동기화 방법은 미정이다.

## 5. 데이터·연차 계산

전체 데이터 사전과 ERD는 [DB설계-V02](./DB설계-V02.md)에 있다. 테이블은 11개, 컬럼은 V01 69개 → 앞선 V02 72개 → 이번 V02 84개로 늘었다.

| 변경 | 내용 |
| --- | --- |
| EMPLOYEE.role | HR_ADMIN / SYS_ADMIN / LEADER / MEMBER |
| LEAVE_HISTORY.idempotency_key | 추가, UNIQUE |
| POLICY.advance_limit_days | 추가, 당겨쓰기 한도, 0은 불허 |
| POLICY.min_staff_floor | 추가, 회사 전체 최소 잔류 인원 하한 |
| DEPARTMENT.min_staff_on_duty | 팀장이 하한 이상으로 설정 |
| LEAVE_TYPE | category, count_basis, max_days, min_tenure_months 추가 |
| LEAVE_REQUEST.leader_confirmed_by | 실제 1차 확인자 FK 추가 |
| NOTICE_FILE | 공지 첨부 메타데이터 7개 필드 추가 |

잔여 컬럼은 두지 않는다. 기간 잔여는 사원의 원장을 `occurred_on >= 기간 시작 AND occurred_on < 다음 기간 시작`으로 합산한다. 기간은 입사일로 계산하고 별도 기간 컬럼을 추가하지 않는다.

- 입사일 기준 부여·기산일 소멸을 유지한다. 원문 기준은 1년 미만 월 1일 최대 11일, 1년 이상 15일과 가산 최대 25일이다. 개근·출근율 예외는 인사 확인 사항이다.
- 대기 신청은 원장에서 차감하지 않고 대기 건수를 안내한다.
- 차감 대상 승인은 실제 휴가 날짜마다 USE 한 행을 기록한다(전일 -1.0, 반차 -0.5). 미래일도 해당 휴가 날짜의 기간으로 구분한다.
- 기산일을 걸치는 신청은 preview·신청 검증에서 거부한다. 미래 기간의 미부여 연차를 예상 부여분에 포함하는지는 미정이다.
- 신청·승인 조건은 **잔여 + advance_limit_days >= 신청일수**다. 대기를 차감하지 않으므로 승인 시 재검증한다.
- 음수 잔여로 마감하면 이전 기간에 ADJUST(+)로 0을 만들고 새 기간에 같은 금액의 ADJUST(-)를 기록한다. 새 GRANT와 합산해 잔여를 계산한다.
- 한도 기본값과 퇴사 시 음수 잔여 처리는 미정이다.

| 코드 | 휴가 | 차감 | 조건 | 잔류 제한 |
| --- | --- | --- | --- | --- |
| ANNUAL | 연차 | 근무일당 1 | 기간 신청 | 적용 |
| HALF_AM / HALF_PM | 오전/오후 반차 | 0.5 | 하루만 | 제외 |
| SICK / OFFICIAL | 병가/공가 | 0 | 잔여 0일에만 노출 | 제외 |
| FAMILY_* | 사유별 경조사 | 0 | 기본 근속 3개월 이상, 종류별 일수·계산 기준 | 적용 |

반차까지 0.5일을 지원하고 시간차는 현재 미적용으로 확정됐다. 필요해지면 DECIMAL(4,1)을 확장하고 시간차 정책을 추가한다.

### 경조사

LEAVE_TYPE.category는 ANNUAL / SICK / OFFICIAL / FAMILY / LEGAL이다. 경조사는 사유별 FAMILY_* 코드로 등록하고 같은 LEAVE_REQUEST·결재·겹침 검사를 사용한다.

- 기본 count_basis는 WORKING_DAYS, 원문 사내 규정의 본인 출산 90일 사례는 CALENDAR_DAYS다. 법정 장기 휴가를 실제 관리할지는 별도 미결이다.
- min_tenure_months=3을 기본 경조사 기준으로 두고, 노출과 신청 API 모두 근속을 검사한다.
- 경조사는 종류·시작일만 받고 endDate는 받지 않는다. 서버가 정해진 일수와 휴일을 반영해 종료일을 계산한다.
- 경조사 상세의 max_days는 정해진 N일로 쓰지만 ERD는 최대 허용 일수로 설명한다. 일부 일수만 신청 가능한지는 확인이 필요하다.
- 잔류 검사는 계산 기준과 무관하게 근무일에만 한다.
- 경조금·화환·조화는 범위 밖이다. 증빙은 우선 인사팀에 별도 제출하며 화면·신청자 메일에 안내한다.
- 증빙 첨부·관계 정보가 필요하면 leave_request_family 1:1 보조 테이블을 검토한다. 현재 ERD에는 포함하지 않는다.
- 출산전후휴가·육아휴직의 관리 범위, 인사 직접 등록, 휴직 상태 필요 여부는 회사 확인 사항이다.

## 6. 정합성·취소·잔류 인원

원장 키는 GRANT:사원:기산일, EXPIRE:사원:기산일, USE:신청:날짜, CANCEL:신청:날짜, ADJUST:UUID, IMPORT:배치:행 형식이다. DB의 idempotency_key UNIQUE로 같은 작업의 중복 기록을 방지한다. 예전 UNIQUE(request_id, type)는 삭제하는 설계다.

승인 순서는 **부서 잠금 → 잔류 인원 검증 → 사원 잠금 → 잔여 조회·한도 검증 → 조건부 상태 변경 → 원장 기록**이다. 업무 변경과 이벤트로그는 같은 트랜잭션으로 처리한다. 최신 핵심 승인 API는 휴가 날짜가 속한 기산 기간의 SUM과 당겨쓰기 한도를 명시한다. 5장에 남은 전체 SUM·한도 제외 예시는 잔존 충돌로 기록한다. 조건부 상태 갱신이 0행이면 409이며 차감 0 종류는 잔여 조회·한도 검사·USE 삽입을 생략한다.

| 검증 | 규칙 |
| --- | --- |
| 중복 기간 신청 | 사원 잠금 → PENDING / LEADER_OK / APPROVED / CANCEL_REQUESTED 겹침 확인 → 삽입 |
| 부서 순환 | parent_id를 따라 올라가 자기 id를 만나면 거부 |
| 재귀 조회 | depth < 10 |
| 잔류 인원 화면 경고 | PENDING, LEADER_OK, APPROVED |
| 잔류 인원 승인 차단 | APPROVED만 집계 |
| 최소 인원 설정 | 팀 값 >= POLICY.min_staff_floor 검증 |
| 실제 최소 인원 | max(회사 하한, 팀 값) |
| 초과 승인 | 팀장의 staff_limit_override가 있어야 허용 |
| 소멸 이후 취소 | 대상 기간 EXPIRE가 있으면 400 거부, 인사가 명시적 ADJUST로 예외 처리 |

직속 부서의 활성 사원을 모수로 하며 연차·경조사에만 제한을 적용한다. 장기 부재자 제외와 반차 포함은 미결이다.

승인 전 취소·반려는 잔여에 영향이 없다. 승인 후 취소요청은 잔여를 복구하지 않으며 인사 취소 승인 시 원래 USE와 대칭인 날짜별 CANCEL(+)로 복구한다. 부분 취소는 새 휴일 처리 절에서는 지원하지 않는다고 명시한다.

## 7. 화면·캘린더

| 역할 | 메뉴 |
| --- | --- |
| 사원 | 대시보드(잔여·대기·알림·공지·신청), 전체 캘린더, 팀 현황, 개인정보(내 정보·신청·연차 이력) |
| 팀장 추가 | 팀 관리, 팀 설정 |
| 시스템 관리자 추가 | 계정·부서·휴일·공지와 첨부·운영 정책·백업/복원·로그·리포트 |
| 인사 관리자 추가 | 최종 결재·취소요청·정정·대리 등록·연차 정책·휴가종류·엑셀 이관·날짜 지난 미처리 N건 |

전체 캘린더는 월 단위이며 부서 필터를 제공한다. 이름과 휴가 종류만 표시한다. **API 응답에 사유 필드를 넣지 않는다.** 병가·공가 종류 자체를 다른 사원에게 공개할지는 추가 확인이 필요하다.

날짜 지난 미처리 신청은 자동 승인·취소하지 않는다. 실제 쉬었으면 인사가 승인 또는 대리 등록하고, 출근했으면 취소한다. 목록 대상 날짜·상태 조건과 별도 API 경로는 아직 없다.

## 8. 알림·공지·로그

- 신청 접수 → 팀장/상위 확인자, 1차 확인 후 → 인사 결재자, 처리 결과 → 신청자 순서로 통지한다.
- 앱 알림과 메일을 사용하고 승인 화면 링크를 넣는다. 메일은 AFTER_COMMIT + Async, 실패 시 재시도한다.
- 화면은 30초~1분 폴링하며 본인 행동 결과는 응답 후 즉시 갱신한다.
- 공지는 MANUAL / SYSTEM, 자동 생성은 초안이다. 관리자가 확인하고 발송하며 사원은 게시된 공지만 본다.
- 공지 첨부는 NOTICE_FILE에 메타데이터를 저장하고 실제 파일은 서버 디스크의 Docker 볼륨에 둔다. 원본명·UUID 저장명을 분리하고 PDF·이미지·오피스 문서 허용 및 크기 제한을 적용한다. 정확한 확장자·용량은 미정이다.
- 첨부 다운로드는 로그인 사용자에게 API로만 제공하고 직접 파일 경로를 노출하지 않는다. 첨부 폴더도 별도로 백업한다.
- 이미 발송한 공지 수정은 알림을 재발송하지 않는다. 공지·알림 행과 실제 외부 메일 처리를 구분한다.
- grant_basis·promote_months는 변경 공지 대상, backup_cron·backup_enabled는 제외다. 새 정책 필드의 공지 여부는 미정이다.
- ACTION_LOG는 append-only, enum 문자열 저장이다. 기존 행위 목록은 로그인·로그아웃 제외를 유지하지만 보안 보완 표에 로그인 실패 기록이 추가됐다. 실패 action·행위자·보관 방식은 미정이며 배치 실패도 남긴다. GRANT·EXPIRE는 사원당 기록한다.
- 로그 action 30종과 인덱스는 DB 문서에 보존했다. 로그의 상세 JSON 전문 검색은 범위 밖이다.
- 촉진은 우선 단순 안내로 구현하는 원문 방향이다. 법정 절차가 필요한지는 회사 확인 후 별도 기록·화면 설계가 필요하다.

## 9. 엑셀 이관·리포트

이관은 **원장만** 생성하고 가짜 승인 신청은 만들지 않는다. 하루 한 행에서 (*)는 0.5일, 없으면 1일이다. 오류 행은 사전에 모아 보여주며 부여분 계산 후 엑셀 잔여·시스템 잔여를 대조한다.

리포트는 항목을 여러 개 골라 항목마다 시트 하나를 생성한다.

| 시트 | 형식 |
| --- | --- |
| 연차 사용 현황 | 한 사람 한 행, 사용일을 가로 날짜 열로 확장 |
| 취소 내역 | 부서 / 이름 / 휴가일 / 취소일 / 사유 |
| 신청 내역 | 부서 / 이름 / 기간 / 종류 / 상태 / 신청일 |
| 병가·공가·경조사 | 부서 / 이름 / 날짜 / 사유 |

- 부서·사원 필터를 제공하며 사원은 이름(부서)로 표시한다.
- 기간은 연도별, 지정 기간, 입사일 기산 기간 중 선택한다.
- 기산일 기준은 사원 한 명만 허용한다. 여러 명이면 서버에서 400을 반환한다.
- 목록형 시트는 기간 지정 필수다.
- 현재 기간: 부서·이름·입사일·기간·총연차·이월·사용·잔여·사용일 열.
- 과거 기간: 부서·이름·입사일·기간·총연차·사용·소멸·사용일 열.
- 잔여는 오늘 기준 최신 값이다. 반차는 (*), 당겨쓴 날짜는 (선)으로 표기한다.
- 당겨쓴 날짜를 새 기간에 중복 표시하지 않는다. 새 기간에는 음수 이월로 표현하며 0이면 이월 열을 숨길 수 있다.
- 리포트 파일은 매번 재생성하는 출력물이다. 취소·복구는 시스템에서 처리한다.

원문의 과거 기간 'EXPIRE 합계 절댓값'과 '당겨쓴 기간은 음수 소멸' 표기는 일치하지 않으므로 산식을 확정하지 않았다. 연간 조회와 사원별 기산 기간이 다를 때 가로 양식을 어떻게 합산할지도 후속 정의가 필요하다.

## 10. 나중에 지정된 휴일

최신 10장과 MVP에 정리된 처리안은 다음과 같다.

1. 휴일 등록·동기화 후 SYSTEM 공지 초안을 만들고 관리자가 발송한다.
2. 해당 날짜에 승인 휴가가 걸린 사원에게 앱·메일로 개별 통지한다.
3. 사원이 취소요청하고 인사가 승인하면 CANCEL(+)로 복구한다.
4. 부분 취소는 하지 않는다. 기간 중 하루만 휴일이 되면 전체 취소 후 재신청한다.
5. 일괄 취소·자동 메일은 불편이 확인되면 2차로 검토한다.

이전 15장의 ADJUST 복구 가정은 제거됐다. 이미 소멸된 기간에는 별도 취소 금지 규칙도 적용되므로 자동 복구로 간주하지 않는다.

## 11. MVP·운영

| 구분 | 기능 |
| --- | --- |
| 포함 | 로그인·역할, 사원·부서·휴가종류, 신청·팀장확인·승인·반려·대기 취소 |
| 포함 | 원장·부여·소멸, 수동 휴일·금지기간·일수 계산, 신청 달력 |
| 포함 | 알림·메일, 엑셀 이관·대조·리포트, 오늘 팀 현황 |
| 포함 | 관리자 대리 등록·삭제·직접 취소, 이벤트로그 기록 |
| 포함 | 회사 전체 캘린더·부서 필터 |
| 이번에 포함 | 취소요청, 공지와 첨부파일, 인사의 날짜 지난 미처리 목록 |
| 후순위 | 공휴일 API, 촉진 메일, 백업·복원 제품 기능, PDF·JSON 출력, 로그 조회 화면 |
| 현재 제외·후속 검토 | 시간차, 회계연도 부여 로직, 경조금·화환·증빙 첨부, 법정 장기 휴가 관리 범위 |

백업은 전체 DB mysqldump, 다른 디스크 저장, 수동·자동 실행 및 복원 확인·로그가 원칙이다. 스키마 관리는 Flyway다. 복구 가능성은 NFR-05에 남아 있으므로 기능 후순위와 초기 운영 대책을 구분해야 한다.

복원은 서버가 생성한 백업 목록에서만 선택하고 업로드한 SQL은 받지 않는다. 복원 시점·사라질 변경 요약을 보여주고 정확한 확인 문구 `예, 정말복원합니다.`를 서버에서도 검사한다. 복원 직전 현재 DB를 자동 백업하고 복원 기록은 DB 외부 파일 로그 및 복원 후 이벤트로그에 남긴다. 첨부 볼륨은 mysqldump에 포함되지 않으므로 별도 백업·복구가 필요하다.

## 12. API 계약

상위 페이지의 응답 구조는 변경되지 않았다. 예시의 상태 코드·문구는 설명용이며 원문에서 빠진 쉼표는 보완했다.

```json
{"success": true, "data": {}}
```

```json
{"success": false, "error": {"status": 400, "message": "요청을 처리할 수 없습니다."}}
```

### 경로·권한

### 핵심 요청·응답·오류

| API | 계약 |
| --- | --- |
| preview | leaveTypeCode·startDate·endDate(경조사는 제외). 저장하지 않고 days·dates·excludedDates·balance(current/after/advanceLimit/pendingCount)·staffCheck·errors·warnings 반환 |
| preview 검사 | 금지 기간, 여러 날 반차, 기존 신청 겹침, 잔여+한도 부족, 기산일 걸침, 근속 미달은 errors. 잔류 초과·당겨쓰기는 warnings. 검사 오류가 있어도 HTTP 200 |
| 신청 | preview 요청 + reason. 같은 계산으로 저장 시 재검증, errors면 400. 성공 201, id·status·days·approver·escalated·warnings |
| 결재자 결정 | 일반 PENDING, 팀장·인사 본인 LEADER_OK, 팀장 부재·미지정은 상위 확인자와 escalated_to |
| 팀장 확인 | staffLimitOverride·선택 comment. 실제 팀장 또는 escalated_to 확인 후 PENDING 조건 갱신, leader_confirmed_by 저장. 성공 200 |
| 팀장 확인 실패 | 관할 밖 404, 이미 처리됨 409, 잔류 초과인데 override 없음 400 |
| 팀장 반려 | reason 필수. 같은 권한·상태 검증 후 REJECTED, 신청자 알림 |
| 인사 승인 | 선택 comment. 부서 → 사원 잠금, 해당 기산 기간 SUM·한도 검증, LEADER_OK 조건 갱신, 날짜별 USE·로그, 커밋 후 신청자·팀장 알림 |
| 인사 승인 결과 | 성공 200에 id·status·days·balanceAfter. 신청 없음 404, 1차 확인 전·이미 처리 409, 한도·잔류 초과 400 |
| 차감 0 종류 | 승인 시 잔여 조회·한도 검증·USE 삽입 생략. balanceAfter 응답과 preview days 의미는 추가 정의 필요 |

preview 잔류 예상식은 teamSize - onLeave - pending - 1(본인)이다. pending은 다른 사람의 대기 신청이며 승인 차단에서는 대기를 제외한다. 원문 예시 수치는 식과 다르므로 그대로 확정값으로 사용하지 않는다. 상세 JSON 예시와 흐름은 [원문 API 설계](./원문/Notion설계-2026-09-21.md#api-설계)에 보존했다.

승인 SQL에는 approved_by·approved_at도 등장하지만 ERD에는 아직 없다. 상세 DTO·페이지 응답 구조와 기타 API의 오류 코드는 추가 설계가 필요하다.

### 보안 보완 방향

CSRF 쿠키 토큰과 SameSite, 모든 변경 API의 IDOR 검사, 병가·공가 only_when_empty 서버 재검증, leader_id 기준 팀장 판정, 민감 사유의 로그 저장 범위, 로그인 실패 기록, POI 파일 크기·압축 공격 방어, 첨부 확장자·크기·UUID 이름·인증 다운로드를 보완 대상으로 명시했다. 이 목록은 Notion 설계 방향이며 구현 완료가 아니다.

## 13. 충돌·확인 사항

| ID | 현재 상태·남은 문제 |
| --- | --- |
| C-01 | 최신 승인 API는 기간 SUM·잔여+한도 검증으로 구체화됐지만 5장 예시는 전체 SUM·한도 제외로 남음 |
| C-02 | 해결: 경고는 대기 포함, 승인 차단은 APPROVED만으로 앞부분도 정리됨 |
| C-03 | 5장 팀장 부재는 연차·반차만, 6장은 모든 승인 휴가. 상세 6장 기준으로 정리 |
| C-04 | 부서 깊이 제한 없음과 depth < 10 병존. 생성 가능 깊이는 미정 |
| C-05 | HR_ADMIN과 hasRole('HR') 불일치가 남음 |
| C-06 | 해결: 팀장·인사 본인 신청은 LEADER_OK로 시작 |
| C-07 | 해결: 휴일 변경의 옛 ADJUST 복원 질문 제거, 전체 취소·CANCEL 복구 유지 |
| C-08 | 음수 마감 ADJUST 두 행과 리포트 EXPIRE 절댓값·음수 소멸 산식은 여전히 불일치 |
| C-09 | 일반 리포트의 날짜별 세로 행과 상세 사용 현황의 사원별 가로 열 병존 |
| C-10 | 해결: 오염된 미결 목록 정리, 시간차는 현재 미적용 명시 |
| C-11 | 해결: 취소요청은 휴일 변경 복구를 위해 MVP에 포함 |
| C-12 | 과거 외부 통신 완료 체크가 제거됨. 실제 SMTP/API 접속 정보와 Google OAuth IT 허용은 별도 확인 |
| C-13 | 병가·공가 종류의 캘린더 공개 범위는 여전히 미결 |
| C-14 | 해결: 신청-원장 ERD가 1:N, USE·CANCEL 날짜별 키로 수정됨 |
| C-15 | EXPIRE 키의 기산일/말일 예시 및 존재하지 않는 신청 occurred_on 참조는 남음 |
| C-16 | 승인 대상 기산 기간과 기산일 걸침 거부는 명시됨. 미래 기간 부여 예상액을 검증에 포함할지는 미정 |
| C-17 | 자동 음수 이월 ADJUST 쌍의 안정된 키·원자성·0/음수 기간 종료 판정 미정 |
| C-18 | FR-41·42와 API 목록 추가. 상세 공지 GET 경로, 미처리 목록 경로·조건, 페이지 DTO 등은 미기재 |
| C-19 | 승인 SQL의 approved_by·approved_at이 ERD에 없으며 leader_confirmed_by와 escalated_to의 기존 설명 정리가 필요 |
| C-20 | 경조사 max_days는 ERD에서는 상한, 상세 신청에서는 고정 일수. 부분 사용·NULL 허용 시 종료일 계산 미정 |
| C-21 | 경조사 본인 출산 90일 CALENDAR_DAYS 사례와 법정 장기 휴가 관리 미결을 구분해야 함 |
| C-22 | 로그인 실패 로그 보완 방향과 기존 로그인·로그아웃 제외/30종 action 목록의 반영 범위 미정 |
| C-23 | 첨부 본문은 DB 경로 저장을 말하지만 ERD에는 stored_name만 있음. 삭제·초안 접근·볼륨 복구 정책 미정 |
| C-24 | preview 예시의 날짜 누락·remaining 수치가 설명과 다름. 차감 0 경조사의 days/이용 일수 및 balanceAfter 의미 미정 |
| C-25 | 세션만으로 권한·퇴사 상태가 자동 갱신되지는 않으므로 기존 세션 재검증·무효화 방법 필요 |
| C-26 | 팀장 본인 신청에서 잔류 미달을 허용할 판단 주체와 수동 상위 전달 흐름은 미결 |
| C-27 | /api/team/today는 사원 API, /api/reports/export는 관리자 API지만 역할별 prefix 밖에 있으므로 권한 예외 정의 필요 |

추가 회사 확인 사항은 장기 부재자·반차의 잔류 집계, 개근·출근율 예외, 병가/공가 0.5일 노출·연간 한도·결재선, 상위 부서장 조회 범위, 회계연도 전환, 당겨쓰기 한도·퇴사 음수 정산, 경조사 증빙·법정 장기 휴가·휴직 상태다. 사용자가 편집 중인 [질문사항.md](./질문사항.md)는 그대로 보존했다.
