# 개발자 문서

이 시스템에 쓰인 기술과 동작 방식을 항목별로 적는다.
각 항목은 **"무엇 = 어떤 방식인가"** 로 시작하고, 이어서 정한 값(시간·횟수), 그렇게 한 이유, 확인한 결과, 관련 코드를 적는다.
값이나 방식을 바꾸면 그 항목을 같이 고친다. 휴가 규칙 자체는 `docs/policy-overview.md`, 설치·운영 절차는 `DEPLOY.md` 에 있다.

마지막 정리: 2026-10-14

## 1. 로그인 방식 (서버 세션)

**로그인 = 서버 세션 방식이다.**

- **흐름**: 로그인에 성공하면 서버가 세션을 만들어 DB(`spring_session` 표)에 저장하고, 브라우저에는 세션 ID 쿠키만 준다.
- **토큰을 쓰지 않는 이유**: JWT 같은 토큰을 브라우저에 두지 않는다. 퇴사·비밀번호 변경 때 서버에서 세션을 지우면 즉시 로그아웃시킬 수 있기 때문이다.
- **DB 저장(Spring Session JDBC)**: 세션을 DB에 두므로 서버를 재시작해도 로그인이 유지된다.
- **세션 쿠키**:
  - `HttpOnly`: 스크립트에서 읽을 수 없다.
  - `Secure`: HTTPS에서만 보낸다(로컬은 끔).
  - `SameSite=Lax`
  - 만료일이 없어 브라우저를 닫으면 끝난다.
- **CSRF 방지**: 서버가 준 `XSRF-TOKEN` 쿠키 값을 화면이 `X-XSRF-TOKEN` 헤더에 실어 보낸다. 다른 사이트가 몰래 요청을 보내도 통과하지 못한다.
- **세션 고정 방지**: 로그인할 때 이전 세션을 버리고 세션 ID와 CSRF 토큰을 새로 발급한다.
- **역할 재확인**: 역할·재직 상태는 세션에 저장된 값을 믿지 않고 요청마다 DB에서 다시 읽는다(`AccountStateFilter`). 역할을 바꾸면 다음 요청부터 바로 적용된다.

관련 코드: `config/SecurityConfig`, `auth/AuthService`, `security/AccountStateFilter`

## 2. 로그인 세션 만료 (자동 로그아웃)

**세션 만료 = 클릭·키보드·스크롤 입력이 10분 동안 없으면 그 브라우저만 자동으로 로그아웃시키는 방식이다.**

- **시간**: 서버 설정 하나로 정한다(`SESSION_TIMEOUT`, 기본 `10m`). 서버가 로그인 응답과 `/api/auth/me` 로 이 값을 화면에 알려 주고, 화면도 같은 시간으로 센다.
- **무엇을 사용으로 치나**:
  - 화면이 사람의 입력(클릭·터치, 키보드, 스크롤)을 센다.
  - 마우스 이동은 치지 않는다. 마우스가 조금만 밀려도 시간이 다시 차는 문제가 있었기 때문이다(2026-10-14).
  - 알림 새로 고침·실시간 갱신처럼 화면이 스스로 하는 요청도 치지 않는다.
- **화면 표시**:
  - 상단 바에 "세션 만료 09:59" 가 줄어들고, 마지막 1분은 주황색이 된다.
  - 1분 전에 안내 창이 뜨고, "계속 사용" 을 누르면 다시 10분이 시작된다.
- **로그아웃 처리**: 시간이 다 되면 `POST /api/auth/idle-logout` 으로 그 브라우저의 세션만 지운다. 휴대폰 등 다른 기기 로그인은 남는다. 저장하지 않은 입력은 묻지 않고 버린다.
- **여러 탭**:
  - 같은 브라우저의 탭들은 마지막 입력 시각을 `localStorage` 로 나눠 본다. 한 탭에서 쓰고 있으면 다른 탭도 로그아웃되지 않는다.
  - 한 탭이 로그아웃하면 나머지 탭도 로그인 화면으로 간다.
- **서버 쪽 만료**:
  - 서버 세션도 10분 동안 요청이 없으면 끝난다.
  - 쓰는 동안은 화면이 2분마다 서버에 알려 연장한다.
  - 화면이 떠 있는 동안은 알림 1분 새로 고침이 서버 세션을 살려 두므로, 실제로 끊는 쪽은 화면의 타이머다.
- **로그인 유지(30일)는 없다**: 2026-10-14 에 없앴다. 로그인 화면의 "아이디 저장" 은 아이디만 브라우저에 기억하고 비밀번호는 저장하지 않는다.

관련 코드: `lib/useIdleLogout.ts`, `components/IdleLogoutWarning.tsx`, `AuthService#idleLogout`, `application.yml` `spring.session.timeout`

## 3. 로그아웃과 강제 로그아웃

**로그아웃 = 버튼을 누르면 그 사람의 모든 기기 세션을 지우는 방식이다.**

- **로그아웃 버튼**: 다른 기기에 열려 있던 화면은 실시간 신호(§6)를 받아 바로 로그인 화면으로 간다.
- **강제 로그아웃**: 퇴사 처리, 비밀번호 재설정 때는 서버가 그 사람의 세션을 모두 지운다(`SessionTerminator`).
- **본인 비밀번호 변경**: 바꾼 그 브라우저만 새 세션 ID로 남고 나머지 기기는 끊긴다.
- **데이터 복원 뒤**: 모든 사람의 세션을 지운다.

## 4. 로그인 시도 제한

**로그인 시도 제한 = 같은 PC(IP)에서 15분 안에 10번 틀리면 그 PC의 로그인을 15분 동안 막는 방식이다.**

- **계정은 잠그지 않는다**: 누가 남의 아이디로 일부러 틀려도 본인은 자기 PC에서 로그인할 수 있게 하려는 것이다.
- **성공 처리**: 로그인에 성공하면 그 아이디로 틀린 횟수만 지운다.
  - 예전에는 IP의 기록을 통째로 지웠다. 그래서 "남의 계정으로 9번 틀리고 → 자기 계정으로 로그인" 을 되풀이하면 제한을 피할 수 있었다(2026-10-14 고침).
- **저장 위치**: 기록은 서버 메모리에 있어 서버를 재시작하면 지워진다(서버 한 대 기준).
- **이벤트 로그**: 로그인 실패는 사용자 칸에 "이름 (아이디)" 로 남긴다.
  - 누가 입력했는지 모르므로 그 직원이 한 일로 연결하지는 않는다.
  - 없는 아이디는 앞 두 글자만 남기고 가린다. 아이디 칸에 비밀번호를 잘못 넣은 경우에 대비한 것이다.

관련 코드: `auth/LoginAttemptService`, `AuthService#loginIdForLog`

## 5. 비밀번호 암호화·규칙·재설정

**비밀번호 암호화 = BCrypt 해시 방식이다.** 비밀번호를 되돌릴 수 없는 값(해시)으로 바꿔 저장하고, 로그인할 때는 입력한 비밀번호를 같은 방식으로 바꿔 비교한다.

- **되돌릴 수 없다**: 복호화하는 방법이 없어 관리자도, DB를 본 사람도 원래 비밀번호를 알 수 없다. 그래서 "비밀번호 찾기"는 알려 주기가 아니라 재설정 링크다.
- **설정**: Spring Security `BCryptPasswordEncoder` 기본값(비용 10 = 2¹⁰번 반복). DB `employees.password_hash` 에 `$2a$10$...` 형식 60자로 들어간다.
- **소금(salt)**: 저장할 때마다 무작위 값을 섞어, 같은 비밀번호라도 사람마다 다른 해시가 된다. 미리 만든 대조표로 한 번에 풀 수 없다.
- **일부러 느리다**: 한 번 비교에 수십 ms가 걸려, DB가 새더라도 비밀번호를 하나씩 대입해 보기 어렵다.
- **없는 계정·퇴사 계정도 비교를 한 번 한다**: 응답 시간만으로 "있는 계정"을 가려내지 못하게 하려는 것이다.
- **72바이트 제한**: BCrypt 는 72바이트까지만 받는다(한글 24자). 그래서 규칙에서 길이를 바이트로 막는다. 예전에는 긴 한글 비밀번호가 500 오류를 냈다.

**새 비밀번호 규칙 = 비밀번호를 새로 정할 때만 검사하는 방식이다.** 지금 쓰는 비밀번호는 다시 검사하지 않는다.

- 8자 이상, 영문·숫자·특수문자 중 2종류 이상, 아이디(이메일 @ 앞부분) 포함 금지, UTF-8 72바이트 이하
- 서버(`PasswordPolicy`)와 화면(`passwordSchema.ts`)이 같은 규칙을 가진다. 바꿀 때는 둘을 함께 고친다.
- **임시 비밀번호**: 관리자가 직원을 만들면 12자(대문자·소문자·숫자·특수문자 각 1개 이상)를 `SecureRandom` 으로 만든다. 첫 로그인 때 바꾸게 한다.

**비밀번호 재설정 = 본인 이메일로 1회용 링크를 보내는 방식이다.**

- **링크 토큰**: `SecureRandom` 32바이트를 Base64URL 로 만든다. DB에는 토큰 자체가 아니라 SHA-256 해시만 저장해, DB가 새도 링크를 만들 수 없다.
- **유효 시간**: 30분, 한 번만 쓸 수 있다. 동시에 두 번 쓰는 것도 막는다.
- **규칙에 걸리면**: 링크를 쓰지 않은 채로 두어 같은 링크로 다시 시도할 수 있다.

관련 코드: `config/SecurityConfig#passwordEncoder`, `auth/password/PasswordPolicy`, `PasswordResetService`, `TemporaryPasswordGenerator`

## 6. SSE 실시간 갱신

**실시간 갱신 = SSE(Server-Sent Events)를 사용해 서버가 클라이언트와의 연결을 한쪽 방향으로 열어 두고, 데이터에 변화가 있으면 바로 "바뀜" 신호를 보내 화면이 새로 불러오게 하는 방식이다.**

새로 고침을 누르지 않아도 다른 사람이 한 신청·승인·취소가 내 결재함·달력·내 휴가에 바로 나타난다.

- **연결**: 로그인한 화면이 `GET /api/realtime` 연결을 하나 열어 둔다.
- **신호 보내기**: 데이터를 바꾸는 요청(POST/PUT/PATCH/DELETE)이 성공하면 서버가 연결된 화면 모두에 신호를 보낸다.
- **신호 내용**: 데이터는 싣지 않는다. 권한 밖의 내용이 새지 않게 하려는 것이다. 화면은 신호를 받으면 지금 보고 있는 데이터만 기존 API로 다시 불러온다.
- **부하를 줄이는 장치**:
  - 숨은 탭은 연결을 끊는다.
  - 0.4초 안에 신호가 여러 번 오면 한 번만 불러온다.
  - 변경한 본인 화면은 자기 신호를 무시한다.
- **연결 유지**:
  - 25초마다 연결 확인 신호(ping)를 보낸다.
  - 30분마다 연결을 끊고 다시 맺는다. 끊겼을 때 놓친 신호가 있을 수 있어 다시 연결되면 한 번 새로 불러온다.
- **신호를 보내지 않는 요청**: 로그인·로그아웃·비밀번호 찾기(`/api/auth/**`). 알림 읽음·내 비밀번호 변경은 본인에게만 보낸다.

**부하 테스트 (2026-10-14)**

연결을 많이 열어 두면 서버에 문제가 생길 수 있어 부하 테스트를 했다. 결과는 **서버 운영에 영향을 줄 만한 문제가 없었다.** 측정은 개발 PC에서 했다. SQL 로그를 켜고 DB 연결이 10개인(운영은 20개)인 불리한 조건이다.

1. **연결을 열어 두는 비용**: SSE 연결을 1,000개까지 열어 보았다.

   | 연결 수 | 서버 스레드 | 메모리(힙) | 1분 CPU | 신호가 모두에게 닿는 시간 |
   |---|---|---|---|---|
   | 0 | 50 | 58MB | 약 2초 | - |
   | 100 | 94 | 71MB | 약 2초 | 56ms |
   | 500 | 94 | 111MB | 약 2초 | 25ms |
   | 1,000 | 94 | 169MB | 약 2초 | 33ms |

   - 연결 하나에 메모리 약 0.1MB가 든다.
   - 스레드는 연결 수만큼 늘지 않는다. 비동기 응답이라 기다리는 동안 스레드를 붙잡지 않는다.
   - 연결 확인 신호로 CPU가 늘지 않았다.

2. **신호 하나에 다시 불러오는 요청 수**: 화면마다 4~7개였다. 달력 7, 대시보드 6, 내 휴가·직원·리포트 5, 결재함·이벤트 로그·정책 4.

3. **모두가 동시에 다시 불러올 때**:

   | 상황 | 요청 수 | 모두 끝나는 시간 | 오류 |
   |---|---|---|---|
   | 대시보드 50명 | 250 | 0.7초 | 0 |
   | 달력 50명 | 350 | 0.9초 | 0 |
   | 달력 200명 | 1,400 | 3.3초 | 0 |

- **결론**: 회사 규모(약 50명)에서는 변경 한 번에 1초 안쪽의 짧은 부하만 생긴다.
- **사용자가 수백 명으로 늘면** 다음을 고려한다:
  - 신호에 바뀐 종류를 실어 관련 화면만 다시 불러오기
  - 다시 불러오는 시점을 탭마다 조금씩 흩뜨리기

관련 코드: `realtime/RealtimeHub`, `RealtimeChangeInterceptor`, `RealtimeConfig`, `lib/useRealtime.ts`

## 7. Cron 자동 작업 (스케줄러)

**자동 작업 = Spring 스케줄러가 cron 식에 적힌 시각(한국 시간)마다 정해진 작업을 실행하는 방식이다.**

cron 은 6칸(초 분 시 일 월 요일)으로 쓴다. 예: `0 0 1 * * *` = 매일 01:00.

| 작업 | 시각 | 하는 일 |
|---|---|---|
| 공휴일 동기화 | 매일 00:10 | 공공데이터포털에서 올해·내년 공휴일을 받아 반영(§9) |
| 연차 부여·재계산 | 매일 01:00 | 직원마다 지금 기간 연차를 부여·재계산, 새 기간이 시작된 직원은 이월·소멸(§10) |
| 연차 촉진 자동 발송 | 매일 09:00 | 정책에서 켰을 때만. 발송 시기에 든 직원에게 알림·메일 |
| 자동 백업 | 설정값(기본 매일 02:00) | §8 |

- **스레드**: 스케줄러 스레드는 2개라 백업이 길어져도 다른 작업이 줄 서지 않는다.
- **실행 기록**: 모든 작업은 실행 결과(성공·실패·건너뜀, 요약)를 남기고, 화면 **정책 › 자동화** 탭에 보인다(`JobRunRecorder`). 작업이 끝나면 실시간 신호를 보낸다.
- **서버가 꺼져 있던 시각의 작업은 나중에 따라 돌리지 않는다.**
  - 연차 부여는 매일 "지금 상태로 다시 계산" 이라 다음 날 실행에서 맞춰진다.
  - 급하면 `POST /api/leave/admin/grant` 로 바로 돌린다.
- **데이터 복원 중**에는 모든 예약 작업을 건너뛴다.
- **새 작업을 만들면** `JobRunRecorder` 로 감싸고 자동화 탭(`AutomationService`)에 등록한다.

관련 코드: `batch/HolidaySyncScheduler`, `batch/LeaveAccrualScheduler`, `batch/JobRunRecorder`, `backup/AutoBackupScheduler`

## 8. 자동 백업과 복원

**자동 백업 = 관리자가 화면에서 정한 cron 시각마다 `pg_dump` 로 DB 전체를 파일 하나로 저장하는 방식이다.**

- **설정이 DB에 있다**: 다른 작업과 달리 시각이 코드에 고정돼 있지 않고 `backup_settings` 표에 있다.
  - 앱이 시작될 때와 설정을 저장할 때 스케줄러에 다시 등록하므로 재시작이 필요 없다.
- **실행 시각 화면**:
  - 매시간·매일·매주·매월·매년·직접 입력 탭에서 버튼(요일, 1일~31일·말일, 1월~12월, 00시~23시, 00분~59분)을 눌러 cron 을 만든다.
  - 고치는 동안 서버가 해석한 설명과 다음 실행 시각 5개가 보인다.
  - 백업은 1시간보다 자주 돌 수 없다.
- **보관**: 최근 N개월(기본 6개월)의 자동 백업은 모두 남기고, 그보다 오래된 자동 백업만 지운다. 수동·복원 전 백업은 자동으로 지우지 않는다.
- **실패하면** 시스템 관리자·인사관리자에게 알림과 메일이 간다.

**복원 = DB를 백업 시점으로 통째로 되돌리는 방식이다.**

- **진행 순서**:
  1. 파일을 확인한다.
  2. 지금 DB를 "복원 전 백업" 으로 남긴다.
  3. 점검 모드로 바꾼다.
  4. 한 트랜잭션으로 모든 표를 비우고 백업 내용을 넣는다.
  5. Flyway 로 지금 버전까지 올린다.
  6. 모든 세션을 지운다.
- **점검 모드 동안**: 모든 API가 503(`MAINTENANCE`)을 돌려주고, 화면은 전체 안내를 띄운다.
- **실패하면**: 한 트랜잭션이라 반만 복원된 상태가 생기지 않는다.
- **끝나면**: 인사관리자에게 완료를, 전 직원에게 "그 시점으로 복원되었습니다" 안내를 보낸다.

관련 코드: `backup/BackupService`, `RestoreService`, `MaintenanceFilter`, `features/policy/CronScheduleBuilder.tsx`

## 9. 공휴일 동기화

**공휴일 = 공공데이터포털(한국천문연구원 특일 정보) API에서 받아 DB에 저장하고, 새 공휴일이 기존 휴가에 걸치면 휴가 일수를 다시 계산하는 방식이다.**

- **받는 범위**: 매일 00:10 에 올해와 내년을 받는다.
- **앱 시작 때**: 올해 공휴일이 하나도 없으면 바로 한 번 받는다.
- **휴가 다시 계산**: 새 공휴일이 걸친 휴가는 차감 일수를 다시 계산해 잔액을 바로잡는다.
  - 근무일이 0일이 되면 자동 취소한다.
  - 같은 동기화를 여러 번 돌려도 두 번 환원되지 않는다.
- **API 키가 없으면** 동기화를 건너뛰고 자동화 탭에 "건너뜀" 으로 남는다.

관련 코드: `calendar/holiday/HolidaySyncService`, `leave/HolidayImpactService`

## 10. 연차 부여·이월·당겨쓴 연차

**연차 = 매일 01:00 배치가 직원마다 "지금 연차 기간" 의 부여량을 다시 계산하고, 새 기간이 시작된 직원은 지난 기간 잔여를 넘기는 방식이다.**

- **잔액 식**: `잔여 = 부여 + 이월 − 사용 − 소멸`
- **연차 기간**: 입사 기념일 기준 또는 회계연도 기준(정책). 기간 경계에 걸친 휴가는 다음 기간 몫을 따로 적는다.
- **매일 다시 계산하는 이유**: 근속 연수, 정책 변경, 늦게 처리된 승인·취소가 모두 다음 날 자동으로 반영되고, 여러 번 돌려도 결과가 같다.
- **당겨쓴 연차**: 마이너스 허용으로 잔여가 음수가 되면, 새 기간이 시작될 때 그만큼을 이월에 **음수로** 넣어 갚는다. 정책 스위치와 상관없이 항상 갚는다(2026-10-14).
- **새 직원**: 만들면 저장이 끝난 뒤 그해 연차를 바로 부여한다.

관련 코드: `leave/LeaveGrantService`, `leave/accrual/*`, `leave/LeaveCharges`

## 11. 휴가 결재와 동시 처리

**결재 = 결재 권한이 있는 한 명이 승인하면 바로 확정되는 1단계 방식이다.**

- **결재 대상**: 신청자의 부서부터 위로 올라가며 처음 만나는 재직 중인 팀장이 결재한다. 인사관리자·시스템 관리자는 모든 신청을 결재할 수 있다.
- **잔액 차감 시점**: 승인할 때 차감하고, 취소가 확정되면 환원한다. 결재 대기 일수는 신청 가능 일수에서 미리 뺀다.
- **검증은 한 곳**: 신청 화면의 미리보기와 실제 신청이 같은 검증(`plan`)을 지나서 둘이 어긋나지 않는다.
- **동시 처리 막기**:
  - 신청과 잔액 표에 버전 번호(`@Version`, 낙관적 잠금)를 둔다.
  - 두 결재자가 같은 신청을 동시에 처리하면 늦은 쪽은 "이미 처리된 신청입니다" (409)를 받는다.
  - 승인할 때 잔액과 겹침을 다시 검사해, 같은 날을 두 번 신청해도 두 번 차감되지 않는다.

관련 코드: `leave/LeaveRequestService`, `common/exception/GlobalExceptionHandler`

## 12. 메일과 알림

**메일 = 데이터 저장이 끝난 뒤(커밋 후) 별도 스레드에서 보내는 방식이다.**

- **실패해도 요청은 성공**: 메일 서버가 느리거나 실패해도 신청·승인 같은 요청은 성공한다. 저장이 취소되면 메일도 나가지 않는다.
- **공통 틀**: 모든 메일은 `MailLayout` 을 쓴다(제목, 표, 버튼 링크).

**화면 알림 = DB에 알림을 저장하고, 상단 종 아이콘이 1분마다(보이는 탭만) 새로 불러오는 방식이다.** 실시간 신호(§6)가 오면 바로 불러온다. 알림의 `type`·`link` 가 버튼과 제목 색을 정한다.

관련 코드: `mail/*MailService`, `leave/LeaveMessenger`, `notification/`, `components/NotificationBell.tsx`

## 13. 이벤트 로그 (감사 기록)

**이벤트 로그 = AOP 로 모든 데이터 변경 요청을 가로채 누가·언제·무엇을·성공했는지 자동으로 남기는 방식이다.**

- **기록 대상**: `/api/**` 의 POST/PUT/PATCH/DELETE 와 엑셀 내보내기. 권한이 없어 거부된 시도도 실패로 남는다.
- **새 API를 만들면** 화면에 보일 이름표를 `AuditLabels` 에 단다.

관련 코드: `audit/AuditAspect`, `audit/AuditLabels`

## 14. 라이선스

**라이선스 = Ed25519 로 서명된 라이선스 문자열을 앱에 내장된 공개 키로 검증하고, 유효하지 않으면 모든 API를 막는 방식이다.**

- **담긴 정보**: 회사명, 만료일, 최대 사용자 수, 설치처(host).
- **검증 방식**: 앱에는 공개 키만 있어서 고객이 라이선스를 위조할 수 없다. 발급 절차는 `LICENSING.md`.
- **로컬**: local 프로필에는 localhost 용 개발 키가 들어 있다.

관련 코드: `license/LicenseService`, `license/LicenseEnforcementFilter`

## 15. DB 마이그레이션 (Flyway)

**DB 구조 변경 = Flyway 가 앱 시작 때 `V{번호}__설명.sql` 을 순서대로 한 번씩 적용하는 방식이다.**

- **현재 상태**: 개발 중 쌓인 것을 2026-10-06 `V1__baseline.sql` 로 합쳤고, 지금은 V14 까지 있다.
- **이미 적용된 파일은 고치지 않는다.** 바꿀 것은 새 번호로 추가한다.
- **엔티티 검사**: `ddl-auto: validate` 라 엔티티와 표가 다르면 앱이 뜨지 않는다.
- **시드 데이터**: 관리자, 정책, 휴가 종류는 마이그레이션이 아니라 앱 시작 때 `config/init/*Initializer` 가 넣는다.

## 16. 입력 중인 화면 보호

**입력 보호 = 서버 데이터를 고치는 화면은 입력을 따로 들고 있다가, 다른 곳에서 바뀌어도 덮어쓰지 않고 안내만 하는 방식이다.**

- **다른 곳에서 바뀌면**: 실시간 신호로 새 데이터가 와도 입력 중인 칸은 그대로 두고 "다른 곳에서 바뀜" 안내를 띄운다(`useServerForm`).
- **저장하지 않고 나가면**: 메뉴 이동·뒤로 가기·로그아웃 때 "저장 / 저장 안 함 / 취소" 를 묻는다(`useUnsavedChanges`).
- **예외**: 세션 만료·복원처럼 강제로 나가야 할 때는 묻지 않고 버린다.
