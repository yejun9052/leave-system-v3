# 개발자 노트: 동작 방식과 숫자

시스템이 **언제, 얼마나, 어떻게** 움직이는지 한곳에 모은 문서다. 휴가 규칙은 `policy-overview.md`, 설치·백업 절차는 `DEPLOY.md`, 보안 설정의 이유는 `SECURITY.md` 에 있다.
숫자를 바꾸면 이 문서도 같이 고친다. 마지막 확인: 2026-10-14.

## 1. 자동 작업(스케줄러)

모든 시각은 **Asia/Seoul**. 실행 결과는 `JobRunRecorder` 가 남기고 화면 **정책 › 자동화** 탭에 보인다. 새 작업을 만들면 `AutomationService` 에도 등록한다.

| 작업 | 시각 | 하는 일 | 건너뛰는 경우 | 코드 |
|---|---|---|---|---|
| 공휴일 동기화 | 매일 00:10 (`0 10 0 * * *`) | 공공데이터포털에서 올해·내년 공휴일을 받아 반영. 새 공휴일과 겹친 휴가는 조정 | API 키(`app.holiday-api.service-key`)가 없을 때 | `batch/HolidaySyncScheduler` |
| 연차 부여·재계산 | 매일 01:00 (`0 0 1 * * *`) | 직원마다 지금 기간 연차를 부여·재계산. 기념일(또는 회계연도 시작일)이 지난 직원은 지난 기간 잔여를 이월·소멸하고, 당겨쓴 연차(음수 잔여)는 새 기간 이월에 음수로 넣는다 | 없음 | `batch/LeaveAccrualScheduler#dailyRecompute` |
| 연차 촉진 자동 발송 | 매일 09:00 (`0 0 9 * * *`) | 발송 시기에 들어온 직원에게 알림·메일 | 정책에서 자동 발송이 꺼져 있을 때 | `batch/LeaveAccrualScheduler#promotion` |
| 자동 백업 | 설정값(기본 매일 02:00, `0 0 2 * * *`) | `pg_dump` 로 백업 파일을 만들고, 보관 기간(기본 6개월)보다 오래된 자동 백업을 지운다 | 설정에서 꺼져 있을 때 | `backup/AutoBackupScheduler` |

- **cron 형식**: Spring 6칸(초 분 시 일 월 요일). 자동 백업만 고정 `@Scheduled` 가 아니다. `backup_settings` 값을 읽어 `TaskScheduler` 에 등록하며, 설정 저장·복원 뒤 다시 등록한다.
- **스레드**: 스케줄러 스레드는 2개(`spring.task.scheduling.pool.size: 2`)다. 백업이 길어져도 다른 작업이 줄 서지 않는다.
- **서버가 꺼져 있던 시각의 작업은 나중에 따라 돌리지 않는다.**
  - 연차 부여는 매일 "지금 상태로 다시 계산"이라 다음 날 실행에서 맞춰진다.
  - 급하면 `POST /api/leave/admin/grant` 로 바로 돌린다.
- **복원 중**에는 `MaintenanceSchedulingAspect` 가 모든 예약 작업을 건너뛴다.
- 작업이 끝나면 `JobRunRecorder.run` 이 실시간 "바뀜" 신호를 보낸다(§3).

**서버가 시작될 때 하는 일**

- 기본 데이터 생성: 관리자 계정, 정책, 휴가 종류, 공휴일. `config/init/*Initializer`(ApplicationRunner)가 하며 마이그레이션이 아니다.
- 올해 공휴일이 하나도 없으면 공휴일 동기화를 한 번 한다(`HolidayStartupSync`).
- 자동 백업 예약을 등록한다.

## 2. 로그인과 세션

| 항목 | 값 | 어디서 정하나 |
|---|---|---|
| 세션 저장 | DB(Spring Session JDBC, `spring_session` 표) | 서버를 재시작해도 로그인 유지 |
| 자동 로그아웃(미사용 만료) | **10분** | `SESSION_TIMEOUT`(`spring.session.timeout`, 기본 `10m`) |
| 자동 로그아웃 안내 | 끝나기 1분 전 안내 창, 상단 바에 남은 시간 | `lib/useIdleLogout.ts`, `components/IdleLogoutWarning.tsx` |
| 로그인 유지(30일) | 없음(2026-10-14 제거). 로그인 화면의 "아이디 저장"은 아이디만 브라우저에 기억 | `features/auth/LoginPage.tsx` |
| 세션 쿠키 | `HttpOnly`, `Secure`(로컬은 끔), `SameSite=Lax`, 만료일 없음(브라우저를 닫으면 끝) | `application.yml` `server.servlet.session.cookie` |
| CSRF | 쿠키 `XSRF-TOKEN` → 헤더 `X-XSRF-TOKEN` | `SecurityConfig` |
| 로그인 시도 제한 | 같은 IP에서 **15분 안에 10번** 틀리면 그 IP의 로그인을 **15분** 막음. 계정은 잠그지 않음 | `auth/LoginAttemptService` |
| 비밀번호 재설정 링크 | **30분**, 1번만 사용 | `AccountMailTemplates.RESET_LINK_VALID_MINUTES` |
| 새 비밀번호 규칙 | 8자 이상, UTF-8 72바이트 이하(한글 24자), 영문·숫자·특수문자 중 2종류 이상, 이메일 @ 앞부분 포함 금지 | `auth/password/PasswordPolicy`, 화면 `passwordSchema.ts` |

**자동 로그아웃이 동작하는 방식**

- **누가 시간을 세나**: 화면이 클릭(터치)·키보드·스크롤 입력을 센다. 마우스를 움직이기만 한 것은 치지 않는다.
  - 알림 1분 새로 고침이나 실시간 갱신처럼 화면이 스스로 하는 요청은 "사용"으로 치지 않는다.
  - 10분 동안 입력이 없으면 `POST /api/auth/idle-logout` 으로 **그 브라우저의 세션만** 끝낸다.
- **여러 탭**: 같은 브라우저의 탭은 마지막 입력 시각을 `localStorage` 로 나눠 본다.
  - 한 탭에서 쓰고 있으면 다른 탭도 로그아웃되지 않는다.
  - 한 탭이 로그아웃하면 나머지 탭도 로그인 화면으로 간다.
- **쓰는 동안**: 2분마다 `/api/auth/me` 를 불러 서버 세션을 연장한다.
- **서버 쪽 만료**: 서버 세션도 같은 10분 동안 요청이 없으면 끝난다.
  - 화면이 떠 있는 동안은 알림 1분 새로 고침이 서버 세션을 살려 두므로, 실제로 끊는 쪽은 화면 타이머다.
  - 숨은 탭은 요청을 보내지 않아 서버와 화면이 거의 같은 때에 끝난다.
- **저장 안 한 입력**: 자동 로그아웃 때는 묻지 않고 버린다(1분 전 안내에 적혀 있음).

**로그아웃 종류**

- **로그아웃 버튼**: 그 사람의 **모든 기기** 세션을 끝낸다. 다른 기기의 열린 화면은 실시간 신호로 바로 로그인 화면으로 간다.
- **자동 로그아웃**: 그 브라우저만 끝낸다. 휴대폰 등 다른 기기 로그인은 유지된다.
- **강제 로그아웃**: 퇴사 처리, 비밀번호 변경·재설정 때 그 사람의 모든 세션을 끝낸다(`SessionTerminator`). 본인이 내 정보에서 비밀번호를 바꾼 그 브라우저만 로그인이 유지된다.
- **역할 확인**: 역할·재직 상태는 요청마다 DB에서 다시 읽는다(`AccountStateFilter`). 역할을 바꾸면 다음 요청부터 바로 적용된다.

## 3. 실시간 갱신(SSE)

누가 데이터를 바꾸면 열린 화면이 새로 고침 없이 바로 바뀐다.

- **연결**: 로그인한 화면이 `GET /api/realtime` 연결을 하나 열어 둔다.
- **신호**: `POST/PUT/PATCH/DELETE /api/**` 가 성공하면 서버가 **"바뀜" 신호만** 보낸다. 신호에 데이터는 없어 권한 밖 내용이 새지 않는다. 화면은 신호를 받으면 지금 보고 있는 데이터만 기존 API로 다시 불러온다.

| 항목 | 값 | 코드 |
|---|---|---|
| 연결 유지 신호(ping) | 25초마다 | `RealtimeHub.HEARTBEAT` |
| 연결 다시 맺기 | 30분마다 서버가 끊고 브라우저가 다시 연결 | `RealtimeHub.TIMEOUT` |
| 끊겼을 때 다시 연결 | 3초(브라우저), 서버가 거절하면 10초 | `RealtimeHub.RECONNECT`, `useRealtime.ts` `RETRY_MS` |
| 신호 묶기 | 0.4초 안에 여러 번 오면 한 번만 다시 불러옴 | `useRealtime.ts` `REFRESH_DELAY_MS` |
| 숨은 탭 | 연결을 끊는다. 다시 보이면 연결하고 한 번 새로 불러옴 | `useRealtime.ts` |
| 신호를 보내지 않는 요청 | `/api/auth/**`(로그인·로그아웃·자동 로그아웃·비밀번호 찾기), `/api/realtime` | `RealtimeConfig` |
| 본인에게만 보내는 요청 | 알림 읽음, 내 비밀번호 변경 | `RealtimeChangeInterceptor.PERSONAL` |

- 변경한 탭은 자기 신호를 무시한다(`X-Client-Id` 헤더 = 탭 ID).
- 요청 밖에서 데이터를 바꾸는 새 작업은 `RealtimeHub.broadcast(null)` 을 부른다.

### 부하 측정 (2026-10-14)

**측정 환경**

- 개발 PC(Windows)에서 복사본 DB로 검증용 서버(18080)를 띄웠다.
- local 프로필이라 SQL 로그를 출력하고 DB 연결 풀이 10개다(운영은 20개). 운영 서버보다 불리한 조건이다.

**1) 연결을 열어 두는 비용**: Node 스크립트로 SSE 연결을 N개 열고 쟀다.

| 연결 수 | 서버 스레드 | 힙 사용 | 1분 동안 CPU | 신호가 모두에게 닿는 시간 |
|---|---|---|---|---|
| 0 | 50 | 58MB | 약 2초 | - |
| 100 | 94 | 71MB | 약 2초 | 56ms |
| 500 | 94 | 111MB | 약 2초 | 25ms |
| 1,000 | 94 | 169MB | 약 2초 | 33ms |

- 연결 하나에 힙 약 0.1MB가 든다.
- 스레드는 연결 수만큼 늘지 않는다. 비동기 응답이라 기다리는 동안 스레드를 붙잡지 않는다. 94개는 연결을 받는 동안 Tomcat 기본 스레드 풀이 늘어난 것이다.
- ping(25초마다)으로 CPU가 늘지 않았다. 1분 2초는 측정 도구(jcmd) 자체의 몫이다.

**2) 신호 하나에 화면이 다시 부르는 요청 수**: 헤드리스 브라우저로 관리자 화면에서 셌다. 공통 3개(`/dashboard/me`, 알림 수, `/license`)가 포함된 수다.

| 화면 | 요청 수 |
|---|---|
| 달력 | 7 |
| 대시보드 | 6 (`/holidays` 를 두 번 부름) |
| 내 휴가, 직원 관리, 리포트 | 5 |
| 결재함, 이벤트 로그, 정책 | 4 |

**3) 모두가 동시에 다시 부를 때**: N개 탭의 요청 묶음을 한꺼번에 보냈다.

| 상황 | 요청 수 | 모두 끝나는 시간 | 오류 |
|---|---|---|---|
| 대시보드 50탭 | 250 | 0.7초 | 0 |
| 대시보드 200탭 | 1,000 | 2.4초 | 0 |
| 달력 50탭 | 350 | 0.9초 | 0 |
| 달력 200탭 | 1,400 | 3.3초 | 0 |

**결론**

- SSE 연결 자체의 부담은 거의 없다.
- 부담은 "변경 한 번 → 화면을 띄워 둔 모든 사람이 다시 불러오기"에서 생긴다. 50명 규모에서는 변경마다 1초 안쪽의 짧은 부하다.
- 사용자가 수백 명으로 늘면 다음을 고려한다:
  - 신호에 바뀐 종류(휴가·직원·정책)를 실어 관련 화면만 다시 부르기
  - 다시 부르기를 탭마다 0~1초 흩뿌리기
- **HTTP(평문) 운영 시**: 브라우저가 한 사이트에 연결을 6개까지만 연다. 숨은 탭은 연결을 끊으므로 탭을 많이 열어도 막히지 않는다.

**다시 재는 법**

1. 복사본 DB로 검증용 서버를 띄운다(`SERVER_PORT=18080`, `DB_URL=.../annual_leave_verify`).
2. 로그인 쿠키로 `GET /api/realtime` 을 N개 연다.
3. `jcmd <pid> Thread.print`, `jcmd <pid> GC.heap_info` 로 스레드·힙을 잰다.
4. `PUT /api/policy`(같은 값)로 신호를 만들어 모든 연결이 `event:change` 를 받는 시간을 잰다.

## 4. 메일

- **발송 시점**: 휴가·계정·공지 메일은 DB 커밋이 끝난 뒤 이벤트(`@TransactionalEventListener`)로 비동기(`@Async`) 발송한다. 메일 서버가 느리거나 실패해도 요청은 성공한다.
- **헬스 체크**: 메일은 제외한다(`management.health.mail.enabled: false`).
